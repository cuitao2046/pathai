# 局域网动态寻址 P0 可行性记录

> 2026-11-01；对应 `specs/local-service-discovery/spec.md` v0.1.3。本文记录代码/官方文档核查与已报告及待执行的真机验证，不把设计依据写作实测结论。

| 项目 | 核对结果 | 结论 |

## 微信官方文档依据（非实测）

- [局域网通信](https://developers.weixin.qq.com/miniprogram/dev/framework/ability/mDNS.html)：同网段、非本机 IPv4 的请求可以用 HTTP 且不进行安全域校验；局域网互访条件不满足时不可用。
- [UDPSocket.send](https://developers.weixin.qq.com/miniprogram/dev/api/network/udp/UDPSocket.send.html)：文档称基础库 2.9.0 起可向 `255.255.255.255` 广播，`setBroadcast` 选项从 2.24.0 起支持；当前项目配置高于该版本，**不能推断目标真机一定支持广播转发**。
- [UDPSocket.onMessage](https://developers.weixin.qq.com/miniprogram/dev/api/network/udp/UDPSocket.onMessage.html)：返回 `message: ArrayBuffer` 和 `remoteInfo.address/port`，候选 IP 应从真实来源提取，再做 HTTP 挑战验证。
- [UserCryptoManager.getRandomValues](https://developers.weixin.qq.com/miniprogram/dev/api/base/crypto/UserCryptoManager.getRandomValues.html)：基础库 2.17.3 起提供密码学安全随机字节；P0 探测轮次使用该接口，真机可用性仍待确认。

## 已实现的隔离探测原型

- 从当前 `D:\code\pathai` 仓库根设置 `PYTHONPATH=backend` 后运行 `python -m pathai_backend.local_discovery_probe`，启动独立 UDP 39001 与 HTTP 39002。不会启动原业务 API，不返回设备身份/签名，也不读取数据库、配对密钥或微信凭据。
- 当前 `master` 为 P0 测试构建，只注册独立探测页 `pages/p0-probe/p0-probe`，移除了启动登录预热；不会加载地图、进入设置页业务自检或访问固定 `API_BASE_URL`。点击“开始探测”后仅广播 `pathai-p0-probe` 的随机轮次、接收 `P0_OFFER`，再访问响应源的无凭据 `/local/p0/probe`；诊断版分别显示随机数、UDP 接口、socket 创建、绑定/发送、异步错误、等待超时和 HTTP 结果。**该响应无身份认证，不能用于设置业务地址，也不能给出可信服务的结论**。
- 客户端探测使用安全随机数且对随机数、UDP、HTTP 各阶段设有时限；重复应答不重复发起探测请求，结束时关闭 UDP socket。服务端限定有效端口、私网来源及有界应答记录，端口被占用会报错而不是另选端口。
- 自动化验证（2026-11-01）：`npx tsc --noEmit` 通过；`npx jest --runInBand` **32 套/260 用例通过，1 套跳过**；仓库根 cwd 下 `python -m pytest backend/tests -q` 通过（1 套既有跳过），`python -m pytest tests -q --import-mode=prepend` **140 通过、1062 subtests 通过**。本机私网地址 `192.168.100.103` 上以独立 UDP 39111、HTTP 39112 完成同机单播→HTTP 探测，HTTP 返回 200 且服务正常关闭；这**仅证明同一台 Windows 主机私网接口上的协议往返**，没有验证微信广播、手机到电脑或跨网络切换。
- 本轮测试准备（2026-11-01，当时状态）：独立服务持续监听 `0.0.0.0:39001/UDP`、`0.0.0.0:39002/TCP`；Windows 当时 WLAN 为公用网络，IPv4 `192.168.100.103/24`，本机通过该地址请求 `/local/p0/probe` 返回 `{"protocol":"local-service-discovery","ready":true}`。经用户确认，临时规则 `PathAI-P0-Probe-UDP-39001-TEMP` 与 `PathAI-P0-Probe-TCP-39002-TEMP` 只允许公用配置下、WLAN 接口、来源 `192.168.100.0/24` 到本机 `192.168.100.103` 的对应入站端口；**测试结束必须撤销这两条规则**，切网后须核对新子网而非继续沿用旧规则。该准备阶段尚无手机实测，后续真机结论见下文。
- 首次目标手机报告（2026-11-01，用户反馈）：iPhone XS Max 运行微信小程序并**自身提供热点**，笔记本加入该热点后点击“开始探测”，旧版页面显示“UDP 或安全随机数能力不可用”。笔记本 WLAN 当时为 `172.20.10.4/28`；旧临时防火墙规则仍限定 `192.168.100.103` 与 `192.168.100.0/24`，不适配新网段。旧提示把 API 缺失、随机数失败/超时、UDP socket 创建/绑定/发送/异步错误合并，故**不能判断具体失败阶段，也不能归因为热点隔离**；且该组合是热点宿主手机运行小程序，属于首版未承诺组合。已将页面诊断细分，等待同机型重新构建并复测；尚未修改防火墙规则，也未取得 UDP/HTTP 连通结论。
- 第二次目标手机报告（2026-11-01，用户反馈）：同一真机调试场景下，新版页面显示“UDP socket 异步报错”。由此可确认微信 UDP 接口存在、安全随机数阶段已通过、socket 创建成功，但旧诊断未记录 `onError.errMsg`，无法确认绑定/发送阶段、具体错误码或广播是否抵达电脑；热点与防火墙均不能单独解释此结果。已增加 P0 页面限定为数字码的错误诊断与绑定/监听阶段显示，待重新编译真机复测。此轮仍未记录跨设备 UDP 或 HTTP 成功。
- 第三次目标手机报告（2026-11-01，用户反馈）：同一 iPhone XS Max 真机调试提示“UDP socket 异步报错（监听/广播阶段）”，未显示数字错误码。可确认 `onListening` 已触发，无法确认 `socket.send` 调用时监听是否已经就绪、广播是否已发送或抵达电脑；当时的旧构建于 `bind()` 后立即 `send()`，阶段显示只反映错误回调到来时的状态。缺少可识别的 `errMsg` 与网络抓包证据，不能归因于热点宿主限制、微信权限或防火墙；同网普通 Wi-Fi、第三方手机热点仍待分别验证。发送时序对照另见后续记录。
- P0 v0.1.3 时序对照准备（2026-11-01，用户批准）：客户端已调整为 `bind()` 后等待 `onListening` 再发送一次广播，监听未就绪 3 秒超时关闭；错误/超时后的迟到回调不能发送。定向单测覆盖监听前不发送、重复监听只发送一次、错误/超时后不发送及既有 HTTP 探测边界。复测须分别记录宿主热点与普通 Wi-Fi/第三方热点，不把单一组合推广为 P0 可行性结论。
- P0 v0.1.3 真机时序对照（2026-11-01，用户反馈）：在原 iPhone XS Max 热点宿主场景重新真机调试，仍显示“UDP socket 异步报错（监听/广播阶段）”，没有数字错误码。按 v0.1.3 发送路径，`send` 仅在 `onListening` 中调用；因此**仅能排除“把发送延后到监听回调即可消除错误”这一修复假设**，不能证明错误是广播参数、iOS 本地网络权限或热点宿主限制引起。笔记本仍为 `172.20.10.4/28`，UDP 39001 和 HTTP 39002 在监听，但临时防火墙规则仍只允许旧地址 `192.168.100.103`/旧网段；它会妨碍跨设备收包，不足以解释手机端 socket 异步错误。本轮未取得跨设备 UDP/HTTP 成功证据；未变更防火墙或业务寻址。
- 普通同网 Wi-Fi 真机成功报告（2026-11-01，用户反馈）：iPhone XS Max 与服务端笔记本连接同一 Wi-Fi，点击“开始探测”后，小程序最终提示“已收到 UDP 响应并连通 HTTP 探测端口”；用户同时在抓包中看到 `{"protocol":"local-service-discovery","ready":true}`，这是 `GET /local/p0/probe` 的 HTTP 响应体而非请求体。笔记本当时 WLAN 为 `192.168.100.103/24`，UDP 39001、HTTP 39002 均在监听。按当前客户端逻辑，成功提示仅在收到匹配本轮随机数的 UDP OFFER、HTTP 200 且响应体 `protocol`/`ready` 均符合预期后出现，故本次**普通同网 Wi-Fi 的无凭据 UDP→HTTP 小程序闭环通过**。仍缺原始抓包源/目的 IP、目标微信/系统版本与不依赖开发调试绕过的发布形态证据；不认定已建立可信设备身份或业务寻址。热点宿主场景的异步错误独立保留。

## Windows＋手机微信真机操作

1. Windows 与手机连接同一 Wi-Fi，确认 Windows 的 WLAN IPv4 为私网地址。先前 `192.168.100.103` 的临时防火墙规则**不适用于**已观察到的 `172.20.10.4/28` 热点网段；切网后重新核对 IPv4/子网与规则，测试结束删除临时规则，不复用旧地址。
2. 在 `D:\code\pathai` 仓库根的 PowerShell 中运行 `$env:PYTHONPATH='D:\code\pathai\backend'; python -m pathai_backend.local_discovery_probe`，确认端口没有被占用；当前测试服务已从该目录启动，无需重复启动。探测器独立于业务后端，**不启动** `backend/.local/start-local.ps1` 也可验证 P0；不要把探测器的 IP 当作业务服务器地址。
3. 在本次 P0 构建的微信真机入口打开小程序，应只看到“局域网连接能力探测”，点击“开始探测”；记录测试时间、手机/系统/微信版本、基础库版本、Wi-Fi 名称、Windows IPv4、网络类型（公用/专用）、防火墙规则与页面结果。出现“已收到 UDP 响应并连通 HTTP 探测端口”仅记为网络探测通过；不发送登录、定位或导航请求。
4. 若只收到 UDP，请检查 TCP 39002、局域网互访及系统权限；若未收到 UDP，分别检查 UDP 39001、广播转发、系统本地网络权限和热点客户端隔离。无法诊断时记为未知，不猜测根因。
5. 在第二个 Wi-Fi 和由**第三台手机**提供的热点重复步骤 1–4；记录每次 Windows IPv4 的变化。若是热点宿主手机运行小程序，单独标为未承诺组合，不与第三方热点混记。
6. **开发工具 `urlCheck=false` 不等于真机放行**。只在可实际验证的微信真机入口及无开发绕过环境下记录结果；如发布/体验版无法访问私网 HTTP，则明确记为阻塞，不将开发版的结果推广到发布版。

## 待目标真机执行的实验

1. 记录 Windows 版本、微信版本、手机型号/OS、微信基础库实际版本、Wi-Fi/热点型号、防火墙网络配置；关闭开发工具绕过后验证 `wx.createUDPSocket`、`bind`、广播发送和单播接收。
2. 对同网段 HTTP 使用无凭据隔离探测服务验证连接；在 Wi-Fi A/B 与第三台手机热点分别测 UDP 与 TCP，可达性拆开记录。
3. 核查 iOS 本地网络权限拒绝/恢复，以及 Windows 公用/专用防火墙状态；拒绝时不误报“服务器未启动”。
4. 选用受维护且兼容小程序的安全随机数、JCS 与 HMAC 能力并对照 Python 测试向量；未完成前不得启用配对/认证的业务模式。

**当前状态：** iPhone XS Max 与笔记本在一组普通同网 Wi-Fi 下的小程序无凭据 UDP→HTTP 探测闭环已通过；iPhone 自身作为热点宿主时 v0.1.3 仍在监听/广播阶段异步报错。v0.1.3 已通过 TypeScript、Jest 32 套/267 用例（1 套/1 用例跳过）、后端 pytest 及仓库根 140 项/1062 subtests。手机微信/基础库版本、第二 Wi-Fi、第三方热点、关闭调试绕过后的发布形态、密码能力及安全准入仍待验证；P0 整体门槛尚未完成，不得将这次无凭据网络探测称作可信业务寻址或进入 P1/P2 业务连接验收。
