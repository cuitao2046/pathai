# 视障危险区标注与路线避让方案

> 调研范围：`d:\code\pathai` 的地图包、拓扑与路由实现、管理入口、指纹/标定/公共空间数据。
> 调研基准：发布包 `backend/maps_data/school-building-01/2026-11-08.2.json`（当前仓库内最新版本）。
> 本文只做调研与设计，未修改任何代码。结论以**代码实际行为**为准；与文档描述冲突处已单列。

## 0. 结论摘要

| 问题 | 结论 |
|---|---|
| 现在能否标注“视障不安全”？ | **只能做边级硬禁行**：把某条边的 `blindAccessible` 设为 `false`（或 `accessibilityLevel` 设为 `999`），盲模式会整条边避开。没有区域、等级、时间段、理由文案的表达能力。 |
| 现在标注后导航会怎样？ | 盲模式重算路线并绕行；若该边是唯一通路，返回 `422 ACCESSIBLE_ROUTE_NOT_FOUND` 或 `422 ROUTE_NOT_FOUND`，**不会告诉用户“因为施工/湿滑”**；普通模式和轮椅模式不受 `blindAccessible` 影响。 |
| 哪些字段看起来有用但其实无效？ | `edges[].riskLevel`、`edges[].walkable`、`nodes[].blindAccessible`、`nodes[].riskLevel`、`floors[].accessibility.riskNodes` **都不参与路线规划**。其中 `riskLevel` 和 `walkable` 在路由归一化时被直接丢弃。 |
| 推荐做法 | 独立“危险区”数据层（不塞进地图包），支持 `block / avoid / notice` 三档、生效时间、理由文案；路由里硬禁行走 `edge_allowed`，软避让走边权惩罚；返回结构化风险提示并让客户端用安全优先级播报。 |
| 最小可用范围 | 边级标注 + 独立 JSON 台账 + 后端注入 + 软/硬约束 + 客户端播报 + 单测；**不做** polygon 绘制、后台 UI、小程序上报、离线快照。可不做数据库迁移。 |
| 最省事 vs 推荐 | 最省事是改一条边的 `blindAccessible` 后重新发布整包；推荐是独立危险层，临时危险不用重发 6MB 地图包，且能“尽量避开 / 禁行 / 仅提示”分级并说明原因。 |

## 1. 现状盘点

### 1.1 地图包与拓扑字段

地图包 schema 定义在 `backend/pathai_backend/map_package/schema.py`：

- 节点 `TopologyNode`（L48-62）：`id/type/coordinates/label/roomType/roomId/doorType/facilityType/rooms/accessible/blindAccessible/wheelchairAccessible/riskLevel/isNormallyOpen`。
- 边 `TopologyEdge`（L65-79）：`id/from/to/distance/accessibilityLevel/walkable/wheelchairAccessible/blindAccessible`。
- 跨层边 `CrossFloorEdge`（L81-94）：同上，另加 `fromFloor/toFloor/type`。
- 楼层 `FloorData`（L120-126）：`topology/geometry/semantic/displayName/level`，且 `extra="allow"`，所以 `accessibility` 等附加块能通过校验。
- 顶层 `MapPackage`（L174-182）：`siteId/mapVersion/publishedAt/coordinateSystem/floors/crossFloorEdges/places/beacons`，同样允许附加字段。

发布包实际数据（2026-11-08.2）中，每条边还带有 `estimatedTime`，每层还有 `geometry.rooms/doors/stairs/elevators/columns/windowSegments/elevatorDoors` 和 `accessibility`。关键事实如下。

| 数据 | 是否存在 | 路由是否读取 | 说明 |
|---|---|---|---|
| `edges[].distance` | 是 | **是** | 唯一基础边权 |
| `edges[].estimatedTime` | 是 | 否 | 仅数据展示，路由用距离重算 |
| `edges[].accessibilityLevel` | 是（0/2/999） | **是** | `999` 在盲/轮椅模式被禁 |
| `edges[].blindAccessible` | 是 | **是** | `false` 在盲模式被禁 |
| `edges[].wheelchairAccessible` | 是 | **是** | `false` 在轮椅模式被禁 |
| `edges[].walkable` | 是（当前全为 true） | 否 | 在 `_norm_edge` 中被丢弃；设为 false 也不会禁行 |
| `edges[].riskLevel` | 是（0.5/5/10） | 否 | 在 `_norm_edge` 中被丢弃；不参与权重 |
| `nodes[].blindAccessible` | 是 | 否 | 路由只检查边的属性，不检查节点 |
| `nodes[].riskLevel` | 是 | 否 | 同上 |
| `floors[].accessibility.riskNodes` | 是（共 121 个点） | 否 | 只被语音 Agent 空间问答和调试渲染读取 |
| `geometry.rooms` Polygon | 是 | 否 | 有真实房间多边形和 `walkablePolygon` 属性 |
| `semantic.rooms` | 是 | 否 | 有 `centroid/public/accessible`，用于语义展示 |
| 危险区 Polygon / 生效时间 / 理由 | **否** | — | 当前完全没有概念 |

当前拓扑规模：

| 楼层 | 边数 | `blindAccessible=false` | `accessibilityLevel=999` | `riskLevel=10` | `walkable=false` |
|---|---:|---:|---:|---:|---:|
| F1 | 360 | 9 | 9 | 9 | 0 |
| F2 | 238 | 7 | 7 | 7 | 0 |

- 这 9/7 条边全部是楼梯接入边，三组字段一一对应；跨层边 10 条（7 楼梯 + 3 电梯），其中 7 条楼梯边 `blindAccessible=false`。
- `riskNodes` 共 121 个：F1 73 个（10 楼梯口 / 3 电梯口 / 60 外开门），F2 48 个（7 / 3 / 38），都带 `coordinates`。
- 也就是说，现有数据里的“不安全”语义**实际上只有楼梯**。地图包没有 `hazardType` 之类的字段；施工、台阶、旋转门、湿滑、人流密集这些语义都无法用现有字段表达，只能新加危险对象。
- 区域（polygon）概念是有的，但目前只用于房间几何（`geometry.rooms` 的 Polygon、`semantic.rooms` 的质心），**没有“危险区 polygon”**；发布包里也没有走廊级的可通行区域图层（源数据里的 `walkable_regions` 没进入发布物）。

### 1.2 路径规划实现

路由引擎是 `src/topology/route_rules.py` 的受限 Dijkstra，后端 `backend/pathai_backend/nav_service.py` 直接消费发布物原始 JSON。

- **边权**（`_edge_weight`，L287-298）：`W(e) = distance + 门类型惩罚`。只在 `room ↔ doorway` 边施加一次门惩罚（swing 0 / fire 0.5 / opening 1.0，常开防火门按 0）。没有通用代价字段，也没有风险权重。
- **硬约束**（`edge_allowed`，L223-238）：盲模式剔除 `blindAccessible=false`、`accessibilityLevel=999`、楼梯跨层边；轮椅模式剔除 `wheelchairAccessible=false`、`accessibilityLevel=999`；**普通模式不做任何剔除**。
- **归一化会丢字段**（`_norm_edge`，L204-218）：只保留 `id/from/to/distance/accessibilityLevel/blindAccessible/wheelchairAccessible/crossFloor/type/doorType/floor`。`riskLevel`、`walkable`、`estimatedTime` 以及未来新增的附加字段都不会进入图。
- **回退链**（`shortest_path`，L363-393）：
  1. 最佳门 + 不穿墙；
  2. 所有门；
  3. 允许穿墙边（`wall_fallback`）；
  4. 跨层绕行。
  四层都会重新调用 `_build_adjacency`，而 `_build_adjacency` 又都会调用 `edge_allowed`。因此：**把新约束放进 `edge_allowed`，硬禁行不会被后续回退层绕过**；放进 `_edge_weight` 的软惩罚也会在所有层生效。
- **不可达降级**（`plan_route`，L234-264）：
  - 盲模式无路 → 用普通模式重算；普通可达则 `422 ACCESSIBLE_ROUTE_NOT_FOUND`，否则 `422 ROUTE_NOT_FOUND`；
  - 盲模式结果是 `wall_fallback` → 直接 `422 ROUTE_NOT_FOUND`；
  - 错误信息是固定文案，不包含危险点原因。
- **发布门槛**（`backend/scripts/convert_map_v9.py` 的 `verify`，L506-561）：要求所有地点在盲模式下可达，否则**不允许发布**。这意味着“在唯一通路上设硬禁行”会卡住发布，而不是让线上出现一个到不了的目的地。
- **响应里的风险提示**（`build_route_info`，L205-211）：只有 `wall_fallback` 会填一条 `riskNotices`，其余路线 `safeForBlind=true`、`riskNotices=[]`。
- **索引层不透传边属性**（`PackageIndex`，`nav_service.py` L47-64）：只保留 `id/from/to/distance/crossFloor/type`，`riskLevel` 等字段在这里已经丢失。后续危险信息必须由导航服务单独注入/组装，不能指望从 `index.edges` 读。
- **客户端**：`riskNotices` 只在 `client/typings/api.d.ts` 里有类型；`client/core/nav/route-overview.ts` 的概要播报不读它，页面也没有展示/播报。后端 `nav_text.py` 会把 `riskNotices` 交给 LLM 改写，但不保证被播出来。

### 1.3 管理/配置入口

| 入口 | 能改什么 | 能否改地图语义 | 结论 |
|---|---|---|---|
| 管理后台（`admin-web`） | 地点 `name/spokenName/type/aliases`、信标 `locationDesc`；查看版本和几何 | 否 | `admin/drafts.py` 的 `_PLACE_FIELDS`、`apply_patch` 只写白名单字段；`admin/publish.py` 还断言只读字段不得漂移 |
| 设置页 | 视障/普通模式等客户端设置 | 否 | 与地图语义无关 |
| 台账文件 | 信标部署台账、标定样本 | 否 | 没有“路段危险”台账 |
| 命令行脚本 | `convert_map_v9.py` 把源 GeoJSON + 信标台账转成发布包 | **间接可以** | 需要人工改源 GeoJSON 的边字段，再转换、重启 |
| 直接改已发布包 | 任意字段 | 技术上可以 | 绕过校验、破坏版本不可变约束，不推荐 |

补充：`admin-web/src/components/MapView.tsx`（L162-168）只画 rooms/columns/stairs/elevators 等几何，没有拓扑边图层；`EditPanel.tsx` 只渲染地点的 `name/spokenName/type`。所以后台不仅没有危险区入口，连“选一条边”的能力都还没有。

因此，“**不改代码就能改地图语义**”的现实路径只有一条：

1. 修改 `result/school_building_01_map_v9.geojson` 中目标边的 `blindAccessible` / `accessibilityLevel`（可选再加 `accessibility.riskNodes`）；
2. 运行 `python backend/scripts/convert_map_v9.py --version <新版本>`；
3. 重启后端（`MapRepository.load` 在启动时一次性加载发布物，CLI 写文件不会热更新运行中的进程）；
4. 用 `--verify-only` 预检，确认没有目的地变成盲模式不可达。

注意：`result/school_building_01_map_v9.geojson` 是 `src/io/geojson_writer.py` 的生成物。重新从 CAD 生成地图会覆盖手工改动，所以它**不是稳定的运营台账**。

### 1.4 指纹/标定/公共空间数据能否复用为危险点锚点

| 数据 | 坐标形态 | 能否复用 | 说明 |
|---|---|---|---|
| 指纹网格 `client/data/fingerprint_grid.ts` | `fpId/floorId/x/y/regionType` | 可以 | `regionType` 已分 `normal/intersection/doorway/high_risk`；`high_risk` 就是楼梯/电梯口，可直接作为点风险锚点或“附近是否有危险”的索引 |
| 标定预置点 `client/data/calibration_points.ts` | `truth: [x,y]/floorId/scene/nearGridId` | 可以 | 20 个预置点，适合现场人员选点；“场景”是标定语义，不是危险语义，需要另加类型 |
| 公共空间/房间 | `geometry.rooms` 的 Polygon、`centroid`、`walkablePolygon`；`semantic.rooms` 的 `centroid/public/accessible` | 可以 | 可直接把“某房间/大厅内危险”挂到房间多边形；但走廊级别的可通行区域（源数据里的 `walkable_regions`）没有进入发布包，所以“走廊区域”目前只能落到边或房间 |
| `accessibility.riskNodes` | `id/type/riskLevel/label/coordinates` | 可以 | 现成的点风险层，已有楼梯口/电梯口/外开门三类；缺施工、湿滑、人流等类型 |
| 地点/信标 | `nodeId` 或 `x/y/floorId` | 可以 | 可作为起终点或最近边吸附的参考 |

结论：**坐标基础设施已经齐全，不需要新建坐标系或采集体系**。缺的是“危险语义对象”和“危险对象到边的编译规则”。

### 1.5 文档与实现的不一致（需要顺带修正）

- `docs/03-地图构建指南.md` §6.3（L219-227）写着“风险标注直接影响路线规划引擎的权重计算，视障模式下规划器会尽量绕开高 r 值节点”，但 `route_rules.py` **没有读取 `riskLevel`**，`_norm_edge` 还会把它丢掉。当前实现与该描述不符。
- `docs/05-路线规划算法.md` §2.2（L76-90）的公式只有“距离 + 门惩罚”，这跟实现一致。
- `specs/phase-1-indoor-navigation/spec.md` REQ-MAP（L213）要求“地图包包含……风险语义”，数据里确实有 `riskLevel/riskNodes`，但它们没有进入导航决策，属于“有数据、无行为”。

无论最终选哪种方案，都建议把 `docs/03` §6.3 改成与实现一致，避免后续按文档误判。

## 2. 分三层结论

### 2.1 现在就能做的（不改代码）

#### 2.1.1 唯一真正影响导航的写法

把目标路段的边设为以下任一组合：

```json
{
  "id": "F1-TE-0122",
  "blindAccessible": false,
  "accessibilityLevel": 999
}
```

- `blindAccessible: false` 是语义最准确的“视障不可通行”；
- `accessibilityLevel: 999` 是现有文档定义的“等价于对视障用户禁用”，同时也会影响轮椅模式；
- 两者只影响**盲模式/轮椅模式**，普通模式仍然会走。

#### 2.1.2 各种字段的实际效果

| 想表达 | 现在可用的字段 | 盲模式效果 | 普通模式效果 | 用户能否被告知原因 |
|---|---|---|---|---|
| 这段路视障禁行 | `edges[].blindAccessible=false` | 整条边硬禁行，绕行；无替代则 422 | 不受影响 | 否 |
| 这段路视障+轮椅禁行 | `edges[].accessibilityLevel=999` | 硬禁行 | 不受影响 | 否 |
| 这个点有风险，但照走 | `floors[].accessibility.riskNodes` | 无 | 无 | 语音 Agent 可回答“哪里有风险”，导航不提示 |
| 这段路风险高，但照走 | `edges[].riskLevel=10` | 无 | 无 | 否 |
| 这段路不可走 | `edges[].walkable=false` | 无（字段被丢弃） | 无 | 否 |
| 这个节点视障不可用 | `nodes[].blindAccessible=false` | 无（路由不看节点） | 无 | 否 |

#### 2.1.3 导航会被影响到什么程度

- **粒度**：只能到“一条拓扑边”。一条走廊可能由多条边组成，需要逐条标注；无法只避开半条边，也无法表达“这个区域”。
- **强度**：只有“完全禁行”，没有“尽量避开”。如果绕行需要多走 200 米，也仍会绕；如果绕不开，就直接失败。
- **失败方式**：唯一通路被禁 → 盲模式无路 → 普通模式可达则返回 `422 ACCESSIBLE_ROUTE_NOT_FOUND`，否则 `422 ROUTE_NOT_FOUND`。文案是通用的，用户不知道是施工、湿滑还是别的原因。
- **发布影响**：`convert_map_v9.py` 的发布门槛会检查所有地点盲模式可达；若硬禁行切断了某个目的地，转换直接失败，地图发不出去。这避免了“线上把用户带到死路”，但也意味着不能靠它做临时封路。
- **普通模式**：完全无效。当前引擎没有普通模式的禁行字段，`walkable=false` 也不生效。
- **客户端告知**：`riskNotices` 只有 `wall_fallback` 才有一条，页面和语音都不消费；所以用户只会看到/听到一个通用错误。

一句话回答“现在能表达什么”：

> **能表达“整条边对视障禁行”，能影响盲/轮椅路线；不能表达区域、等级、时间段、原因，也不能影响普通模式；不可达时只能整体报错，不会解释原因。**

#### 2.1.4 操作步骤（不改代码）

```powershell
# 1. 编辑 result/school_building_01_map_v9.geojson，把目标边的 blindAccessible 改为 false
# 2. 预检（不写文件）
python backend/scripts/convert_map_v9.py --version 2026-11-14.1 --verify-only
# 3. 正式生成新版本
python backend/scripts/convert_map_v9.py --version 2026-11-14.1
# 4. 重启后端，让 MapRepository 重新加载发布物
```

适用场景：**长期、确定、不可通行的结构性风险**，例如某段楼梯、某扇长期封闭的门。不适合施工围挡、地面湿滑、临时人流这一类会变化的危险。

### 2.2 应该怎么设计

#### 2.2.1 推荐数据模型：独立“危险区”对象

不要复用 `riskLevel`。它现在的值是按节点类型推导出来的（0.5 普通、5 玻璃门类、10 楼梯口），既没有“施工/湿滑/人流”的语义，也没有分级和时间；把运营危险塞进去会和结构风险混在一起。

推荐新增 `HazardZone`（危险区）：

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `hazardId` | string | 是 | 稳定 ID，如 `HZ-20261114-0001` |
| `siteId` | string | 是 | 场所 |
| `floorId` | string | 是 | 楼层；跨层危险拆成多条 |
| `targetType` | `edge/area/point` | 是 | 录入形态 |
| `edgeIds` | string[] | 边级必填 | **路由真正使用的锚点**；区域/点也必须先编译成边 |
| `geometry` | GeoJSON | 否 | 区域/点的显示与录入形态；边级可省略 |
| `type` | enum | 是 | `construction/stairs/revolving_door/wet_floor/crowd/glass_door/obstacle/other` |
| `level` | `block/avoid/notice` | 是 | 禁行 / 尽量避开 / 仅提示 |
| `appliesTo` | string[] | 否 | 默认 `["blind"]`，可扩到 `wheelchair/normal` |
| `reason` | string | 是 | 短文案，如“走廊施工，围挡占道” |
| `spokenText` | string | 否 | 语音专用；缺省按 `type` 生成模板 |
| `penaltyM` | float | 否 | `avoid` 的距离惩罚，默认 60 米 |
| `activeFrom` | datetime | 否 | 为空表示立即生效 |
| `activeUntil` | datetime | 否 | 为空表示长期有效；临时危险必须填 |
| `status` | `pending/active/resolved/rejected` | 是 | 用户上报默认 `pending` |
| `source` | `admin/field_survey/user_report/voice` | 是 | 来源 |
| `reportedBy` | string | 否 | 用户上报主体（脱敏存储） |
| `createdAt/updatedAt` | datetime | 是 | 审计 |
| `revision` | int | 是 | 乐观并发/客户端缓存失效 |

**边 vs polygon 的结论**：

- 路由的计算单位是边，所以**最终必须落到 `edgeIds`**。
- 记录形态推荐支持三种：
  - 边级：运营最常用，直接选走廊中心线，精确、无几何歧义；
  - 区域：施工围挡、积水片、活动人群，画 Polygon，保存时与同层所有边做“线段-多边形相交（含 0.3~0.5 米缓冲）”，把命中的边写入 `edgeIds`；
  - 点级：用户上报“我在这里遇到障碍”，按最近边吸附，写入单条 `edgeIds`。
- 区域只作为“录入/展示形态”，不作为运行时几何计算；这样路由保持确定性，也不需要每次请求做空间查询。
- MVP 可以先只做 `edge`，区域和点后续加；数据模型预留 `targetType/geometry` 即可。

**等级设计**：

| 等级 | 语义 | 路由行为 | 典型场景 |
|---|---|---|---|
| `block` | 确认不可通行 | 硬禁行，所有回退层都不放行 | 施工完全封路、地面塌陷、消防封锁 |
| `avoid` | 能走但应尽量绕开 | 边权加 `penaltyM`，有更短替代路线时自然绕行 | 湿滑、人流密集、临时堆放、围挡占半幅 |
| `notice` | 可以走，但必须提醒 | 不改路线，路线经过时播报 | 玻璃门、外开门、台阶前、照明暗区 |

默认建议：**运营标注默认 `avoid`，只有现场确认完全不可通行才用 `block`**。这样可以避免“一标注就 422”的体验，也避免发布门槛被临时事件卡死。

#### 2.2.2 存储与版本：独立危险层，不塞进地图包

推荐把危险区放在**独立的可变数据层**，与不可变地图包解耦：

- 地图包继续负责几何/拓扑/结构无障碍（`blindAccessible`、楼梯、电梯）；
- 危险层负责运营/临时风险（施工、湿滑、人流、临时障碍）；
- 路由请求时加载“当前生效”的危险区，按 `mapVersion`/`siteId` 绑定，注入 `RouteGraph`；
- 危险层有独立的 `hazardVersion`（可用 `max(updatedAt)+count` 或单独版本行），在 `RouteInfo` 中返回，便于客户端缓存和问题追溯。

为什么不用“把危险区写进地图包”：

- 地图包约 6 MB，临时危险每次都要重新生成、发布、下载整包；
- 地图包是不可变的，改一次就产生新版本，历史版本会快速膨胀；
- 施工现场的危险可能几小时就变化，跟“地图版本”不是一个时间尺度；
- 发布门槛会要求所有目的地盲模式可达，临时 `block` 可能直接卡住发布。

如果确实需要离线展示，可在发布时把危险区**快照**写入地图包的附加字段（`extra=allow` 已支持），但路由仍以在线危险层为准；快照只用于地图上画危险区。

#### 2.2.3 路由里怎么落

推荐在 `RouteGraph` 构造时注入一个按 `edgeId` 索引的危险表，而不是把危险字段塞进每条边：

```text
RouteGraph(raw_data, hazards={
  "F1-TE-0122": {"level": "avoid", "penaltyM": 60, "reason": "...", "hazardId": "..."},
  "F1-TE-0123": {"level": "block", "reason": "...", "hazardId": "..."},
})
```

具体落点：

1. **硬禁行**：在 `edge_allowed(e, mode)` 里判断 `hazards[edge_id].level == "block"` 且 `mode` 在 `appliesTo` 中 → 返回 `False`。
   - 因为四层回退都会走 `edge_allowed`，`wall_fallback` 也无法绕过硬禁行。
   - 这是必须显式测试的点：现有 `wall_fallback` 是为了保连通，不能让它把施工封路“悄悄放回来”。
2. **软避让**：在 `_edge_weight(e)` 里加 `penaltyM`：
   - 默认 60 米；可按危险类型/等级覆盖；
   - 同一条边有多个 `avoid` 时取最大值（或最大值 + 少量叠加），避免惩罚失控；
   - 软惩罚在所有回退层都生效，所以“最佳门/所有门/跨层绕行”都会优先避开。
3. **仅提示**：不改 `edge_allowed` 和 `_edge_weight`，只在结果里记录“路线经过了该危险区”。
4. **模式过滤**：`appliesTo` 默认 `["blind"]`；施工类可以配 `["blind","wheelchair","normal"]`，但普通模式目前没有禁行语义，需要本次一并加，不能指望现有字段。

**不可达时的降级策略（推荐）**：

| 情况 | 行为 |
|---|---|
| 软避让绕不开 | 正常返回路线；`hazards` 里标记 `passed`；`safeForBlind` 保持 `true`；播报“前方为施工区域，已尽力避开，请谨慎通过” |
| 硬禁行导致盲模式无路，普通模式有路 | 返回 `422 ACCESSIBLE_ROUTE_NOT_FOUND`，`details` 带 `blockedHazards`（类型、位置、原因、建议）；**不要**静默改用普通路线 |
| 硬禁行导致两种模式都无路 | 返回 `422 ROUTE_NOT_FOUND`，`details` 带 `blockedHazards` |
| 目的地本身在 `block` 区域内 | 在“确认目的地/创建会话”阶段就失败，返回 `422 DESTINATION_BLOCKED`（新错误码），提示换目的地或联系工作人员；不要先把用户带上路再报错 |
| 起点本身在 `block` 区域内 | 优先吸附到最近的安全节点；没有安全节点则 `422 ORIGIN_BLOCKED` |
| `wall_fallback` + 危险区 | 保持现有规则：盲模式不公开 `wall_fallback`；危险区不能改变这个安全边界 |

**响应契约建议**：

```json
{
  "safeForBlind": true,
  "hazardVersion": "2026-11-14T09:30:00Z/3",
  "hazards": [
    {
      "hazardId": "HZ-20261114-0001",
      "type": "construction",
      "level": "avoid",
      "reason": "走廊施工，围挡占道",
      "floorId": "1",
      "edgeIds": ["F1-TE-0122"],
      "action": "avoided",
      "position": { "x": 12.3, "y": 45.6 }
    }
  ],
  "riskNotices": ["已为您避开一处施工区域，路线略有绕行。"]
}
```

- `riskNotices` 保留，兼容现有 LLM 改写链路和 `wall_fallback` 文案；
- `hazards` 是给客户端做结构化播报/展示的权威字段；
- `action` 区分 `avoided/passed/blocked`，客户端据此决定“概要播报”还是“行前安全提示”。

#### 2.2.4 播报与客户端

现状是“后端有 `riskNotices` 字段，但客户端不播”。推荐补齐：

- **路线概要**：创建会话后，在“全程约 X 米”之后补一句“已为您避开 N 处危险区域”；如果有 `passed` 的 `notice/avoid`，补“途经 1 处施工区域，请注意”。
- **行前提示**：路线经过 `notice` 危险区时，在进入该段前的决策点用 `priority: "safety"` 播报；客户端已有安全抢占队列（`client/core/speech/speech-queue.ts` L159-164），可直接复用。
- **不可达**：422 时播报具体原因和建议，而不是“没有路线”；提供“换目的地/联系工作人员/结束导航”的可访问选项。
- **地图展示**：危险区用高对比色块/粗线段 + 文本标签；屏幕阅读器可聚焦，读出 `type + reason`；不要把颜色作为唯一信息通道。
- **离线/缓存**：危险层是小数据（几 KB），可在会话创建时随路线响应下发；地图页如需提前展示，可加 `GET /sites/{siteId}/hazards?activeAt=` 轻量接口。

#### 2.2.5 标注的录入方式

| 入口 | 适用 | 交互 | 权限/流程 | 改动量 |
|---|---|---|---|---|
| 管理后台 | 长期/半长期危险 | 地图上点选边、画多边形、填类型/等级/原因/有效期；列表可“解除” | 管理员直接生效；写审计 | 新增 router + 表 + 前端页面 |
| 台账 JSON + CLI | 批量导入、离线整理、演示 | `result/hazards_school-building-01.json`，CLI 校验/导入 | 运维执行；可 dry-run | 最小，无需 DB |
| 小程序端上报 | 临时障碍、用户亲历 | “报告此处有障碍”按钮/语音；自动带当前楼层/坐标/最近边；默认 `avoid/pending`，可拍照 | 用户上报待审核；可信工作人员可即时生效；按 openid 限流 | 中，需新页面/接口/审核 |
| 语音上报 | 免手操作 | 导航中说“这里不好走/有障碍”，意图识别后落一条 `pending` | 同上 | 中，接 REQ-VOICE |

录入规则建议：

- 用户上报默认 `level=avoid`、`status=pending`、`activeUntil=now+24h`；工作人员确认后才能升为 `block`。
- 临时类型预设有效期：湿滑 2 小时、人流 24 小时、施工 7 天、结构性问题长期；到期自动失效，管理端可续期。
- 所有新增/修改/解除写审计（可复用现有 `AdminAuditEvent`）。
- 不允许普通用户直接创建 `block`，避免恶意封路。

#### 2.2.6 与现有字段的关系

- **保留** `blindAccessible/accessibilityLevel` 表达结构性、永久性的不可通行（楼梯、无坡道门槛）。它们已经进入发布门槛和测试，不要为了临时危险去改。
- **不要复用** `riskLevel` 表达运营危险；它的值域和语义是按类型推导的，混用会让“楼梯 r=10”和“施工 r=10”无法区分。
- `walkable=false` 目前是死字段：要么在路由里补上（普通模式也禁行），要么在文档里明确“不生效”，避免运营误用。
- 节点级 `blindAccessible/riskLevel` 目前也是死字段；如果要做“节点危险”，应统一到危险层，不要再扩节点字段。
- 如果必须让普通模式也避让，需要新增普通模式的 `edge_allowed` 逻辑；现有普通模式是无条件放行的。

## 4. 需要产品确认的点

1. 默认等级：运营标注默认 `avoid` 还是 `block`？建议默认 `avoid`，只有现场确认不可通行才 `block`。
2. 普通模式是否也要避让？建议数据模型支持，但首期只对盲模式生效，避免改变现有普通用户体验。
3. 用户上报是否即时生效？建议 `pending` + 24 小时 TTL，工作人员确认后升级；可信工作人员账号可即时。
4. 目的地被 `block` 时：直接失败并建议换目的地，还是引导到最近安全点？建议直接失败，避免把视障用户带到封锁区边缘。
5. 区域粒度首期是否要做？建议 MVP 只做边级，polygon 作为第二阶段；数据模型预留 `targetType/geometry`。
6. 危险数据保留与隐私：用户上报是否存 `openid`、照片保留多久？建议只存脱敏主体 ID，照片按现有隐私策略定期清理。

## 附：一句话回答

- **现在最省事**：把要避开的边改成 `blindAccessible=false`，重新转换发布地图。盲模式会绕开整条边，绕不开就报错；普通模式无效，用户也不会知道原因。
- **推荐做法**：建独立危险层，用 `block/avoid/notice` 三档 + 生效时间 + 理由，路由里硬禁行走 `edge_allowed`、软避让走边权惩罚，响应带结构化风险提示并由客户端安全播报。临时施工不用重发地图包，也不会因为封路卡住发布。
