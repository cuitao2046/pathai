# 开发规范（项目开发制度）

> **性质**：本文件是 PathAI 项目的流程与工程制度，所有新会话、新成员开工前必读。
> **效力**：与 `specs/` 冲突时以 spec 为准（spec 是需求事实源）；本文件约束「怎么做」。
> **更新**：制度变更须在此追加并同步 `README.md` 索引；不要散落到临时笔记。
> **当前版本**：2026-10-27（首次固化）。

---

## 1. 需求与规格流程（SDD）

- `specs/` 是唯一需求事实源。任何功能/交互变更**先改 spec**（版本号 + 变更说明 + §10 决策记录），
  经用户确认后再动代码。
- 较大改动先在 `.trae/documents/` 写实施计划，用户批准后执行。
- 产品/架构/算法口径看 `docs/01`–`docs/24`；`docs/25` 是**真机验收口径**，spec 变更必须同步它。
- 不得在代码里实现 spec 未描述的行为；规格与实现冲突时停下来澄清，不擅自取舍。

## 2. 踩坑与决策记录（强制）

- 每解决一个关键问题/坑，**必须追加**到 `docs/问题与踩坑日志.md`（文末时间正序）：
  时间戳、问题描述、解决方案；必要时补根因、涉及文件、教训。
- 开工遇到异常先在该文档与 `docs/设计决策记录.md` 检索同类条目，避免重复踩坑。
- 阶段成果与变更脉络记入 `docs/项目迭代日志.md`。

## 3. 客户端架构分层

- 单向依赖：`pages/`（编排、canvas 绘制、手势）→ `services/`（装配、业务服务）→ `core/`（纯逻辑）。
- `core/` **零 wx 依赖**，必须可单测；wx 能力用依赖注入（`connect`/`fs`/`audioFactory`/`credential`）。
- **单页架构**：`app.json` 仅 `pages/map/map`、`pages/settings/settings`；语音、意图、导航全部并入地图页。
- 模块级单例 `appContext` 按配置装配 mock/live；替代开关写 kv，**重启小程序生效**。
- `Page({data})` 字面量只在模块首次加载时求值一次：进入页面读取的初始化逻辑放 `onShow`。
- 常量单一来源：客户端 `client/config/env.ts`，管线 `src/common/constants.py`；禁止散落硬编码。

## 4. 测试与回归

- 客户端：`cd client` → `npx tsc --noEmit` → `npx jest`；后端：`pytest`（**固定仓库根 cwd**）。
- 三步回归分开执行、逐条检查退出码，不看截断后的汇总行。
- **mock 必须使用真实地图包 `2026-10-25.1` 与真实信标数据**，禁止虚构（`client/tests/fixtures/real-map.ts`）。
- 协议/平台假件必须复刻状态语义（SocketTask `readyState`、时序、fake timers 下持续供样），
  否则时序 bug 会溜进真机。
- 大计算量用例显式放宽超时（30s）；新增/修改逻辑须补可回归的断言，测试自身错误也要修正而非放宽。

## 5. 工程硬约束

- 地图包文件化存储，文件 sha256 即 ETag；微信 storage 单 key ≤1MB → 地图本体走文件缓存。
- **新地图包发布后必须立即重启本地后端**（`backend/.local/start-local.ps1`），否则进程内仍是旧版本；
  重启后用 `GET /api/v1/sites/{siteId}/map?version=latest` 核对 `mapVersion` 与 `dataSha256`，
  不能只看磁盘文件名。客户端需冷启动（或重新进入小程序）才会切换到新版本。
- **已下发过的地图版本号不得原地重写**：内容有任何变化都必须递增 `日期.序号`（如 `.1→.2`）。
  同名不同内容会让已缓存/续传的客户端出现 sha 与半成品错位（真机表现为 416）。
- 大文本 sha256 用异步分片版（`utils/sha256.ts` 的 `sha256Async`），同步版仅用于小文本。
- 密钥只存后端环境变量（`PATHAI_XFYUN_*`），客户端零密钥；原始音频不入业务后端。
- 后端同步 SQLAlchemy 2 + Session，schema 演进用 alembic；本地 sqlite 置于 `backend/.local/`（gitignore），
  Demo 必须显式 `PATHAI_DATABASE_URL`；本地启动必须 `--host 0.0.0.0`。
- 无障碍：标注固定 12px 屏幕字号 + 白描边 + 贪心防重叠；位置不可信不推进显示，**不伪造位置**。
- 调试/一次性脚本放 `debug/`，根目录不留 `.py`；本地密钥脚本 `backend/.local/start-local.ps1` 不入库。

## 6. Git 与提交

- 按 `README.md`：**禁止直接在 master 工作**，一分支一需求，分支名不带斜杠（`feature-xxx`）；
  合入 fast-forward only，合入后删除分支。
- 提交信息用 Conventional Commits：`feat|fix|test|docs|refactor(scope): 英文主旨`，正文说明「为什么」。
- 只提交本次变更涉及的文件，禁止 `git add -A` 夹带无关改动；密钥/数据库/缓存文件不入库。
- 用户明确要求「直接提交 master」时才在 master 提交。

## 7. 文档与交付同步

- spec 变更 → 同步 `docs/25` 验收步骤与踩坑日志（如涉及）。
- 新增用户可见能力 → 检查 `docs/25`、`README.md` 索引是否需要更新。
- 不新建无必要的文档；已有文档优先扩写，避免信息裂成多份。

---

## 8. 单次变更的执行顺序

1. 读 spec / 相关 docs，确认需求与验收口径；
2. 涉及规格变更则先改 spec 并请用户确认；
3. 改代码（分层、依赖注入、常量集中）；
4. 补/改单测，跑 `tsc` + `jest`（后端改动再加 `pytest`）；
5. 用真实数据自检边界（地图包、信标、协议真机/冒烟）；
6. 追加踩坑日志；同步 `docs/25` / spec；
7. 提交（分支按 §6），向用户汇报改动点与复测指引。
