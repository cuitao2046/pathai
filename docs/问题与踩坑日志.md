## [回溯补录·第一阶段] 小程序服务类目二级分类不符被驳回

- **问题**：工具类目下没有「其他工具」二级分类，强行选择不匹配的工具二级分类，
  审核因「功能与类目不符」被驳回。
- **解决**：改选「交通服务 → 导航/地图」；该类目个人主体不支持，需学校/组织主体注册。

## [回溯补录·M 阶段] sqlite :memory: 多连接不共享表

- **问题**：测试用 `sqlite:///:memory:` 时每个连接各自一张库表，第二条连接找不到表。
- **解决**：测试改用**临时文件库** + `Base.metadata.create_all` 建表；
  另注意 auth 响应字段是 `accessToken` 而非 `token`。

## [回溯补录·C7] 含时间戳请求的 Idempotency-Key 哈希比对触发 409

- **问题**：请求体含 `observedAt` 等时间戳字段，两次「相同」请求哈希必然不同，
  幂等键比对判为冲突返回 409。
- **解决**：测试把请求体冻结为模块级常量后再取幂等键。

## [回溯补录·C7] 到达判定边界与幂等键重放历史会话

- **问题**：样例地图 (5,5) 坐标距终点恰 5m（`ARRIVAL_RADIUS_M=5.0`）一拍即到达，
  「非到达更新」测试误判；固定 openid + 固定幂等键会重放历史到达会话污染状态。
- **解决**：非到达更新用距终点 >5m 的坐标（如 (4,4)）；幂等键保证唯一性。

## [回溯补录·地图转换] v9 数据孤立节点与割点房间导致另一翼不可达

- **问题**：v9 真实地图有 27 个孤立/不可达节点，且 F2 生物工作室等割点房间被
  基线路由引擎规则 1/3 拒绝穿房路径 → 另一侧翼不可达。
- **解决**：转换脚本保留**最大连通分量**，割点房间提升为 intersection
  （保留 `promotedFromRoom` 标记）；F2 东翼 3 地点仅经 accessibilityLevel=999
  楼梯平台连通属源数据事实，verify 归类为警告、API 层返回 422 `ACCESSIBLE_ROUTE_NOT_FOUND` 属正确行为。

## [2026-10-25·回溯补录] mock 测试全面换真实地图/信标数据后的连锁坑

- **问题**：所有 mock 测试改用真实地图包 2026-10-25.1 与真实信标后集中暴露：
  ① 三点定位用「相同 RSSI」观测会几何退化被判 unreliable（真实信标散布大）；
  ② MAP_VERSION_CONFLICT 的派生第二版 `publishedAt` 若不晚于真实包，latest 会反转；
  ③ 真实地点名无楼层前缀且 aliases 全空，意图/地点查询须按最长匹配+同名多处语义重写；
  ④ 导航到达/偏航选点必须用真实节点坐标并冻结几何前提断言。
- **解决**：按上述四点重写用例；jest 用 `declare const require` 跨目录引真实地图 JSON，
  fixture 放 `client/tests/fixtures/real-map.ts` 模块级缓存。

- **问题**：安卓系统下扫不到 iBeacon，与代码权限无关。

## [2026-10-26·回溯补录] 真机 ERR_CONNECTION_REFUSED / 网络连接不可用

- **问题**：真机请求后端失败：`localhost` 在真机上指向手机自身；
  或后端未启动/只监听 127.0.0.1；或防火墙未放行；或手机与电脑不同 WiFi。
- **解决**：`API_BASE_URL` 用开发机**局域网 IP**；后端必须 `--host 0.0.0.0` 启动；
  放行 TCP 8000 入站规则；三查同 WiFi。

- **问题**：开发机地址多轮变化（192.168.100.103 → 192.168.1.28 → 192.168.68.108 → 192.168.1.28），
  真机连不上后端。
- **解决**：更新 `client/config/env.ts` 的 `API_BASE_URL` + docs/25 §1.2 表格并提交，

## [2026-10-26·回溯补录] 开发者工具增量编译漏新文件（反复踩）

- **问题**：新增/删除的 TS 文件未进模块表，运行时报 `module 'xxx' is not defined`，
  表现为整页无响应或白屏。
- **解决**：「工具 → 清除缓存 → 全部清除」后重编译；**删增文件后必做**。

## [2026-10-26·回溯补录] 同步 sha256 大文件阻塞主线程数十秒

- **问题**：真机上对 4.6MB 地图包同步算 sha256，逻辑层阻塞几十秒，
  表现为「正在加载地图」期间整页点击无响应（PC 工具快不易察觉）。
- **解决**：走分片异步版 `utils/sha256.ts` 的 `sha256Async`（macrotask 让出主线程）；
  异步组装摘要直接 `toHex`，误用 `sha256Hex` 会二次哈希。同步版仅用于小文本。

## [2026-10-26·回溯补录] 微信 storage 单 key 上限 1MB

- **问题**：4.6MB 地图数据 `setStorageSync` 必失败（被 kv 降级吞掉只存进程内存，冷启动丢失）。
- **解决**：地图本体走**文件缓存**（`wx.getFileSystemManager` 用户目录，
  `utils/map-cache.ts`）：启动配对（缓存摘要+文件）秒开；服务端 sha 一致免下载，
  不同则后台异步覆盖（下次启动生效，不热替换以免导航会话版本冲突）。

## [2026-10-26·回溯补录] touch 手势绑定吞掉子控件 tap

- **问题**：手势事件绑在整个地图容器上，容器内楼层切换/全图按钮的 `bindtap`
  在真机无法合成，点击无反应。
- **解决**：手势改绑 **canvas 自身节点**；所有覆盖控件设显式 `z-index`。

## [2026-10-26] 单分包 2048KB 硬限击穿端侧 WASM 路线

- **问题**：真机上传失败 `subpackage /subpackages/asr/ source size 12842KB exceed max limit 2048KB`。
  实测包体规则：主包 ≤2MB、**单分包 ≤2048KB（以错误信息为准，此前"单包限制已放开"的判断有误）**、
  合计 ≤30MB；`WXWebAssembly.instantiate(path)` **只接受代码包内路径**（下载 wasm 的路线不通）。
  减重攻坚：13.15MB wasm 经 wasm-opt -Oz + brotli(q11/lgwin24) 压到 **2281KB 仍超**（限 2048KB）；
  备选三个死胡同：① `asr-main`(10.6MB) 缺配套 glue，EM_ASM 表与主 glue 不匹配、shim 后初始化挂死；
  ② `vad-asr`(11.7MB，可压到 1967KB) 只有 Offline+VAD 导出、**无在线识别器**，且其离线 zipformerCtc
  拒绝固定 T=77 的流式模型（ORT `invalid dimensions x[1]: Got 561 Expected 77`）。
- **解决**：离线路线判死，整体切换**讯飞在线 WebSocket**（首启即联网）；
  Sherpa 分包/模型下载/后端静态路由/冒烟脚本全部删除，2048KB 超限问题随之消失。

## [2026-10-26] 引擎契约假识别器 isReady 恒 true 导致死循环

- **问题**：Sherpa 契约单测的假识别器 `isReady()` 恒返回 true，
  引擎 `while (recognizer.isReady(stream)) decode(...)` 同步死循环烧 CPU，
  jest 看似卡死（node 进程 CPU 飙升 174s+）。
- **解决**：假识别器状态随 decode 递减（喂帧 +1、decode -1）。

## [2026-10-26] 讯飞真机排障：先给引擎加分段埋点

- **问题**：真机按住说话无反应且无任何报错，无法判断断在凭据、连接、录音还是服务端。
- **解决**：给 `XfyunAsrEngine`/`XfyunTts`/装配层加 vConsole 分段日志
  （`[app] 数据源` → `[xfyun-asr] 会话开始 → 凭据就绪 → 连接建立 → 首帧已发 → 识别完成/失败`），
  断在哪一环即定位哪一层；结论固化在 docs/25 §1.5。

## [2026-10-26] 设置页数据源切换对导航页/首页不生效（编译期常量 bug）

- **问题**：导航页与首页用 `DEFAULT_DATA_SOURCE`（编译期常量）判断 mock/live，
  设置页写入的 kv 覆盖被无视——切了 live 导航页仍跑 mock。

## [2026-10-26] query_location 意图客户端无处理分支，永远停在过渡话术

- **问题**：语音「我在哪儿」后界面一直显示"请稍等，正在查询您的当前位置"——
  后端返回的过渡话术被播报后，客户端**从未发起定位查询**（applyIntent 无分支）。
- **解决**：新增 `services/location-query.service.ts` 单次定位查询：
  造观测源（mock 模拟轨迹/live 实扫）→ LocationPipeline 主动 tick（绕开 standby 8s 节流）→
  按 FE-01 质量策略出播报（reliable 报楼层+地点附近、degraded 仅楼层、
  失败/10s 超时统一"暂时无法可靠确定当前位置"，**不伪造位置**）。

## [2026-10-26] 定位接口 400：rssi strict int 遇上中位数偶数平均的小数

- **问题**：`POST /api/v1/locations/estimate` 返回 400，错误信封 `INVALID_REQUEST`。
  根因（pydantic 复现确诊）：窗口聚合每信标取 RSSI 中位数，**偶数样本取平均产生 -57.5**，
  而契约 `rssi: int` 为 strict 拒绝带小数的浮点（`int_from_float`）。mock 源 500ms 密集发样，
  偶数样本是常态必踩；导航页 mock 轨迹走同一管线同样中招。
- **解决**：`core/ble/scan-window.ts` 的 median 偶数分支 `Math.round` 取整（dBm 整数语义）；
  测试补 `.5` 样本断言整数防回归。

## [2026-10-26] 文档≠实测：超拟人合成请求 text 必须 base64

- **问题**：按官方文档明文示例发 `payload.text.text`，真实网关返回
  `10163 ... field 'text' must be encode to base64 string`。
- **解决**：`xfyun-tts.ts` 请求帧 text 改 `utf8ToBase64`。
  **教训：单测只能对照文档公式，协议真实差异必须靠真实服务冒烟暴露**——
  本次用标准库手写最小 ws 客户端（客户端帧须掩码）做了「签名握手 101 → 协议帧往返
  → 合成落盘 mp3」全链路冒烟，同法也验证了听写链路。

## [2026-10-26] 微信 wss 自定义请求头真机不稳 → 讯飞鉴权选 URL 签名

- **问题**：讯飞超拟人鉴权方式一要求 `x-api-key` 请求头，但微信社区实测
  WebSocket 自定义 header「手机端/工具正常、电脑端小程序不生效」，官方社区亦建议
  不手动设置握手头。
- **解决**：采用**方式二 URL 签名**（与听写同构，后端签发、零 header 依赖、多端一致）；
  方式一仅作为无 key/secret 时的备选并标注 PC 端边界。

## [2026-10-26] fake timers 单测：窗口类组件必须持续供样

- **问题**：LocationQueryService 首版测试「未在驱动窗口内收敛」——
  假观测源只在 start 发一次样本，fake 时钟被 advance 推进后样本恰好被
  50ms 窗口的严格 `>` 边界剔除 → 永远凑不齐 3 个信标、永不发请求。
- **解决**：假源改为 `setInterval` **持续供样**（与真实源周期发射同语义），
  任意 tick 时刻窗口都有新鲜观测；另注意 jest `-t` 过滤是**正则**（`+` 等是元字符）。

## [2026-10-26] 同一条 shell 命令里 cd 换目录后 pytest 跑空（复发两次）

- **问题**：三重回归写成一条命令——先 `cd client` 跑 tsc/jest，紧接着跑
  `pytest backend/tests`，此时 cwd 已是 client/，pytest 报
  "no tests ran / file or directory not found"（exit 4）；因为前面 jest 全绿，
  只看截断输出容易误判。
- **解决**：回归拆开执行，**pytest 固定用仓库根 cwd**（工具 cwd 参数或独立命令）；
  每一步显式检查退出码，不以截断后的汇总行为准。

## [2026-10-26] mock 文本「改了没缓存」连修两次：受控 input 不回显 + data 字面量只算一次

- **问题**：设置页模拟识别文本改完二次进入仍显示默认值。第一次只补了 kv 写入与启动恢复，
  仍复现；根因有两层：① `input value="{{mockText}}"` 是**受控组件**，但 `bindinput`
  里只写存储、**没有 setData 回显**——页面 data 停在旧值；② 小程序 `Page({data})` 字面量
  **只在模块首次加载时求值一次**，同进程再次进入页面不会重新执行读取逻辑。
- **解决**：`onMockTextInput` 同步 `setData({mockText})`；`onShow` 每次进入都
  `getMockAsrText()` 回读缓存兜底（任意进入时序都正确）。
  **教训：小程序受控 input 必须 setData 回显；依赖"进入页面时"取值的初始化
  逻辑要放 onShow，不能只放 data 字面量/onLoad。**

## [2026-10-26] 关闭导航后文字提示卡"复活"遮挡地图

- **问题**：点「关闭」收起导航 HUD 后，居中反馈卡又弹出来挡住地图。
  根因：`onDismissNav` 只复位了导航字段，**没清 `fallbackText`/`reply` 等面板字段**；
  居中卡的显示条件是 `!navActive && (… || fallbackText !== '')`——`navActive=false`
  后，导航期间 TTS 降级累积的 `fallbackText` 恰好成为卡片重新显示的理由。
- **解决**：抽共享方法 `onDismissIntent()` 清空全部面板字段，`onDismissNav` 收尾时调用；
  PTT 开始新一轮对话时也先收旧卡；居中卡加右上角「✕」关闭按钮——
  反馈面板任何时刻都可收起，不再永久遮挡地图。
  **教训：浮层的"打开条件"由多个字段驱动时，任何退出路径都必须把参与判断的字段
  全部复位，否则 A 面板会借 B 面板的残留字段复活。**

## [2026-10-26] 真机语音播报失败：TTS 在 socket 未 OPEN 时就 send

- **问题**：真机日志 `[xfyun-tts] 合成/播报失败: SocketTask.send:fail SocketTask.readyState is not OPEN`，
  表现为「语音播报不可用」降级。根因：`XfyunTts.speak()` 注册完回调后**立即 send**——
  微信 SocketTask 在 CONNECTING 状态 send 直接 fail；ASR 引擎有 onOpen→泵帧流程，TTS 漏了这一环。
  单测没拦住是因为假 socket 的 `send` 只记录数组、**未模拟 readyState 语义**。
- **解决**：请求帧移入 `onOpen` 回调发送 + 8s 握手超时兜底（未 open 即关闭按"连接失败"归类）；
  假 socket 补 `CONNECTING/OPEN/CLOSED` 状态机（非 OPEN 的 send 调 fail，errMsg 与真机一致），
  并加防回归用例「未 open 不发送、open 后才发」+「握手超时 reject」。
  **教训：协议类假件必须复刻目标平台的关键状态语义（readyState/时序），
  "发了就算过"的宽松假件会让整类时序 bug 溜进真机。**

## [2026-10-26] 全量并发下大计算量用例超 jest 默认 5s（复发性 flaky）

- **问题**：`sha256.test.ts` 的 52 万/百万字符双跑 sha256 用例在**全量套件并发**时
  偶发 `Exceeded timeout of 5000 ms`（单独跑必过）——此前两次"未捕获到名字的偶发失败"即此。
- **解决**：三个大计算量用例显式 `timeout 30000`（逻辑不变，消除满载机器的误报）；
  连跑 3 轮全量 227 通过验证稳定。
  **教训：长计算用例必须显式放宽超时；"单独跑过、全量挂"优先怀疑默认超时与并发负载，
  而非被测逻辑。**

## [2026-10-27] 非「开发调试」模式打开：socket 域名未配置直接拒连

- **问题**：不从真机调试进入，而是从微信**小程序列表**直接打开，启动语音输入即报
  `createSocketTask:fail wowss url not in domain list`，随后降级「语音播报不可用，已切换为文字提示」。
- **根因**：微信客户端对 socket 强制校验「socket 合法域名」；讯飞两个 wss 域名尚未在
  小程序后台配置。「不校验合法域名」（开发者工具）与手机端「开发调试」**只对该调试模式生效**，
  正常打开路径一律校验，代码层无法绕过。

## [2026-10-27] 前后端路径距离差 0.01m：Python round 与 JS Math.round 不同口径

- **问题**：`test_route_rules_consistency` 的后端↔前端 Dijkstra 对拍偶发失败，
  报 `28.41 != 28.42`、`73.45 != 73.46` 这类 0.01m 差异；换一次拓扑（采样点集变化）
  就冒出 13 条，看起来像「测试太严」。
- **根因**：**同一份浮点权重、两种舍入规则**。后端 `round(dist, 2)` 是 Python 的
  「就近取偶」，前端 `Math.round(dist*100)/100` 是「半数向上」。在 `.xx5` 半分位
  （如 28.415）两者必然分叉；而 `dist*100` 又受二进制表示影响（`128.185*100` 落在
  `.5` 两侧），所以哪些点会红完全取决于拓扑。
  测试里的「JS 复刻」当时用的是 `round(dist*100)/100`——也是 Python 的 round，
  于是复刻本身就不等于真 JS。
- **解决**：新增 `src/common/rounding.py::round_distance`（纯标准库，不依赖 shapely），
  显式复刻 `Math.round`：`floor(v*10^d + 0.5)/10^d`。`route_rules._dijkstra` 与
  对拍测试的 JS 复刻都改用它，保证同一份权重出同一个两位小数。
  期望值用 Node 实测 `Math.round(v*100)/100` 逐条核对（28.415→28.42、73.455→73.46、
  128.185→128.19、42.325→42.33、2.675→2.68、1.005→1.0）。
  新增 2 条单测：一条锁「与 JS 一致」，一条锁「内置 round 在这些边界上确实不同」，
  防止有人改回 `round()`。
- **教训**：
  1. **跨语言对拍先对齐舍入，别先放宽容差**：0.01m 不是噪声，是口径不同；
     真正的修法是把两侧收敛到同一个函数，容差只应覆盖真正的浮点累加误差。
  2. **「复刻」要验证复刻本身**：测试里的代理实现在 `.xx5` 上也会跑偏，
     写复刻时用另一种语言/真实现实测几个边界值，否则对拍等于自说自话。
  3. 该口径只统一**路径距离**；`nav_service` 的指令剩余距离仍是展示用舍入，
     如后续要和服务端显示严格一致，同样换成 `round_distance` 即可。

## [2026-10-28] 地图断点续传：首片必须带 Range，网络错误不能当 416 重置

- **问题**：按"已下载偏移 > 0 才发 `Range`"实现时，首片走整包 200，一次拿完 4.6MB，
  分片进度与续传形同虚设；又把网络失败与 `416` 一起当作"半成品失效"重置为 0，
  结果中断后静默整包重下，断点续传实际上从未生效（单测里看不出来，因为最终文件仍正确）。
- **根因**：
  1. `wx.request` 只有带上 `Range` 才可能拿到 206；不带 Range 的"首片"永远整包返回；
  2. 网络中断与"服务端判定偏移越界"是两类错误，混在一个 `catch` 里重置会掩盖真实故障。
- **解决**：
  1. 始终发送 `Range: bytes=offset-(offset+1MiB-1)`，服务端支持则 206 + `Content-Range`，
     不支持则按 200 整包兜底写入；已下载字节每片持久化到 storage，重启按偏移续传；
  2. 只有 `ApiClientError.statusCode === 416` 才清空半成品重下，其余错误原样抛出；
  3. 半成品文件按 `siteId + mapVersion` 隔离，版本变化即丢弃；完整性校验对象是
     **拼接后的完整字节**（`sha256BytesAsync`），校验通过才转正为正式缓存。
- **教训**：
  1. 分片协议必须以"每片都带 Range"为前提，否则服务端永远返回整包，续传是假功能；
  2. 测试要断言**请求头里的偏移**（是否出现 `bytes=0-` 重下），只看最终文件内容会漏掉这类退化；
  3. 文本 JSON 不能按字符串切段下载（UTF-8 多字节会被切断），必须按字节追加、最后一次解码。

## [2026-10-28] 地图半成品二进制读回失败：readFile 无 encoding 的返回值不可信

- **问题**：首片建档修复后，下载能走完分片，却在完整性校验前报
  `[map] 地图加载失败 ApiClientError: 地图半成品读取失败`（map-service 读半成品处）。
  同时真机日志里出现一次 `map/data 416`，说明本地还留着「已下满」的续传状态。
- **根因**：
  1. `readMapPartialBytes` 用 `readFile`（不带 encoding）后以
     `res.data instanceof ArrayBuffer` 判定类型；真机/工具的二进制回调返回值
     未必能命中宿主环境的 `instanceof ArrayBuffer`，判定失败即返回 null，
     于是刚拼好的 4.5MB 文件被判为「读不出来」；
  2. 服务端（当时进程仍是旧代码）不支持 Range 一律 200 整包，客户端 200 分支
     先删半成品再整包写入，链路本身没问题，只是校验那一步卡住；
  3. 真机 416 来自续传状态 `downloadedBytes == 总字节` 的合法越界请求，
     客户端按设计清空半成品重下，属正常路径，不是故障。
- **解决**：
  1. 完整性校验改为**只读一次文本**（`readMapPartialText`，`encoding: 'utf8'`），
     再用 `sha256Async(raw)` 按 UTF-8 字节分片哈希与服务端 `dataSha256` 比对；
     JSON 文本 UTF-8 往返编码字节一致，校验语义不变，同时省掉一次 4.5MB 读盘；
  2. 删除 `readMapPartialBytes`（避免再踩 `instanceof` 坑），半成品读失败改为
     记录 `errMsg`，下次日志可直接看到失败原因；
  3. 后端补支持 Range（本次重启前进程仍是旧代码），实测
     `bytes=0-1048575 → 206`、`bytes=<总长>- → 416`；
  4. 新增「服务端不支持 Range 时整包 200 兜底」用例，避免只测 206 路径。
- **教训**：小程序里判断二进制返回值不要用 `instanceof ArrayBuffer`
  （跨上下文/桥接对象会失真），能用文本+显式编码就用文本；另外**后端改了代码必须重启**
  才算生效，否则客户端测得的是旧协议（本例一度以为 416 是异常，其实是新旧协议混跑）。

## [2026-10-28] 真机 map/data 416：同名版本被原地重写 + 续传偏移越过文件末尾

- **现象**：真机重启小程序，`GET .../map/data?version=2026-10-28.1` 返回 416；
  而服务端对 `Range: bytes=0-1048575` 实测正常返回 206，说明服务端行为正确。
- **根因**：
  1. 当天为修正信标功率把 `2026-10-28.1` **原地重写**（版本号不变、sha 变了），
     设备先前已缓存/续传旧内容，与新的 `dataSha256` 错位；
  2. 客户端续传偏移取自持久化的「已下载字节」，当它等于文件总长而半成品尚未转正时，
     `Range` 起点正好等于 EOF → 服务端按 HTTP 语义返回 416；
  3. 旧逻辑只在 `offset > 0` 时处理 416，首片 416 会直接抛给用户。
- **解决**：
  1. 数据侧：发布 `2026-10-28.2`（内容与 .1 相同、版本递增），保留 .1；词典 `map_version` 同步；
     后端重启后 `latest` 与 `dataSha256` 均指向 .2。
  2. 客户端：续传偏移 ≥ 总长时直接清空重下，不再发越界 Range；**任意 416 都清空半成品并重试一次**。
  3. 规范：已下发过的版本号禁止原地重写，内容变化必须递增 `日期.序号`。
  4. 补 2 条 jest 回归：满偏移不发越界 Range、首片 416 自动重试。
- **涉及**：`client/core/map/map-service.ts`、`client/tests/map-download-resume.test.ts`、
  `backend/scripts/convert_map_v9.py`、`backend/maps_data/school-building-01/2026-10-28.2.json`、
  `tests/testutil.py`、`docs/开发规范.md`。
- **教训**：
  1. **版本号是缓存契约的一部分**：「同名覆盖」在断点续传/ETag 体系里等价于数据损坏，
     哪怕只改一个字段也必须递增版本；
  2. 416 是服务端的正确响应，**客户端必须自愈**（清空+重下），不能把协议错误暴露给视障用户。

## [2026-10-28] 根目录脚本导入 pathai_backend 可能命中旧仓库安装包

- **问题**：在仓库根执行 `python -c "import pathai_backend.location_solver"` 时，
  解析到 `D:\code\pathai\backend\pathai_backend\...`（另一份旧 checkout 的 editable 安装），
  而不是当前工作区 `D:\code\pathai1`；`module.__file__` 才是判断依据。
- **解决**：`src/tools/fit_location_params.py` 在导入前把当前仓库 `backend/` 与仓库根
  插入 `sys.path` 最前，确保使用当前代码；跨目录共享的 Python 包一律显式限定路径。
- **教训**：测试通过不等于用的是当前代码；涉及工作区外的同名包时，先打印
  `module.__file__` 确认来源，再下结论。
