## 1. 为什么必须实测（问题的量化）

生产解算的 RSSI→距离模型用错了基准参数，且项目内部同时存在**三套互不相同的口径**：

| 位置 | 用作「1m 参考 RSSI」的值 | 路径损耗指数 n | 说明 |
|---|---|---|---|
| **生产解算** `backend/pathai_backend/location_solver.py` | 取 `beacon.txPower` = **-10**（实为**发射功率**） | 2.0 | ❌ 语义错配 |
| **客户端 mock** `client/core/ble/mock-beacon-source.ts` | 同上取 `beacon.txPower` = **-10** | 2.0 | ❌ 与解算"互逆"→ 闭环自洽 |
| **后端测试** `backend/tests/test_location_api.py` | `TX_POWER = -10.0` | 2.0 | ❌ 与被测实现同源，测不出问题 |
| **分析脚本** `debug/qa_gdop_independent.py`、`debug/probe_beacon_contribution.py` | `RSSI_REF_1M = **-50**` | **3.5** | ✅ 概念正确（同文件还并存 `TX_POWER = -10`） |
| **AT 清单占位** `docs/reference/beacon_at_commands_*.md` | `C5` = **-59** | — | 占位值，从未实测替换 |
| **厂商手册示例**（P13） | `C2` = **-62** | — | 设备/环境相关 |

**实测验证**（真实地图包 2026-10-27.1，取真实信标坐标作真值点，合成 RSSI 后跑生产解算）：

| 合成基准 | 观测 RSSI | 解算结果 |
|---|---|---|
| -59（物理合理） | -53, -69, -69, -69, -70 | **无坐标，`unreliable`**（残差超限） |
| -10（＝当前实现） | -4, -20, -20, -20, -21 | 误差 **0.1 m**，`reliable` |

- `rssi_to_distance(-70, -10)` = **1000 m**；同一个 -70 按 -59 算是 **3.5 m**。
- **安全属性成立**：基准错配时系统**拒绝服务**（判 `unreliable` 不给坐标），不会输出错误坐标，
  符合 REQ-LOCATION「宁可进入恢复状态，也不得猜测」。
- **但功能不可用**：live 数据源下真机定位**永远拿不到可用坐标**。这也解释了此前真机 live 定位
  从未真正验收通过——mock 与单测用的是同一个错误基准，**全绿是自洽的假象**。

**-50 / -59 / -69 三个候选值的来源差异**（说明为何不能拍脑袋）：
- `-50`：项目内部分析脚本的经验值（配 `n=3.5`，含重度室内衰减假设）；
- `-59`：0 dBm 档设备的典型 measured power（仓库 AT 清单占位）；
- `-69`：本次部署显式把发射功率降到 **-10 dBm**，1m 处参考值应同步下降约 10 dB 的推算值。

→ **必须现场实测才能冻结**，这正是 `docs/24` 要求「所有数值 `[TBD]`，标定后写入服务端配置并版本化」的原因。

## 2. 待冻结参数清单（标定产出物）

| 参数 | 现状 | 标定后去向 |
|---|---|---|
| `rssiAt1m`（1m 参考 RSSI，measured power） | 概念缺失，被 `txPower` 顶替 | 新增字段；后端配置项 |
| `n`（路径损耗指数） | 硬编码 2.0 | 后端配置项；支持按楼层/信标分组 |
| `RESIDUAL_RELIABLE_M` / `RESIDUAL_DEGRADED_M` | 硬编码 1.5 / 4.0 | 由实测残差 RMSE 分布反推 |
| `ORIGIN_MIN_CONFIDENCE`、`confidence` 映射 | 硬编码 | 由静态 CEP 统计确定（`docs/24` §4） |
| RSSI 合法范围、快照新鲜度时限 | -100~-20 / 10s | 由遮挡实验确定（`docs/24` §4） |
| 偏航阈值、到达停留时长 | 工程默认 | 由动态路线记录确定（BE-05） |

## 3. 工具划分（关键设计决策）

**决策：只新建 1 个小程序 + 1 个 PC 脚本，动态采集不新建工具。**

| 环节（`docs/24` 步骤） | 由谁承担 | 理由 |
|---|---|---|
| 1 布设真值标定点（10–20 个） | **人工 + 纸质/表格**，点位录入标定小程序 | 真值坐标来自图纸 + 激光测距，工具只负责登记 |
| 2 静态采集（每点 60–120s、3–5 次、跨时段） | **新建 `positioning-calibrator` 小程序** | 需长时间停留采集 + 多点管理 + 环境备注，fingerprint-collector 是"走到点拍快照"，语义不同 |
| 3 动态采集（沿 3–5 条已知路线步行） | **复用主小程序 `client/` + 新增「标定模式」** | 动态记录需要**服务端事件**（偏航/到达/跨层），只有主小程序有完整导航链路；新建工具等于重造导航 |
| 4 数据分析 → 参数初值 | **新建 `src/tools/fit_location_params.py`（PC）** | 回归/CEP/阈值统计需可复算、可审计；**不在小程序里做统计** |
| 5 记录与冻结 | PC 脚本产出参数版本文件 + 人工写入配置 | 与 `docs/24` §5 一致 |

**沿用既有工程范式**：`positioning-calibrator` 复制 `fingerprint-collector/` 的 BLE 扫描封装
（`utils/beacon.js`）、导出机制（`USER_DATA_PATH` JSON + 剪贴板 + 分享）、页面风格；
**不合并进 `fingerprint-collector`**（指纹库采集与参数标定的记录语义不同，混在一起会污染指纹数据）；
也**不合并进 `beacon-provisioner`**（后者要连接写 AT 特征值，权限与风险面不同）。

## 4. `positioning-calibrator` 小程序设计

### 4.1 目录结构（拟）

```
positioning-calibrator/
├── app.js / app.json / app.wxss        # 场地配置、操作人、设备信息
├── data/reference_beacons.js           # AUTO-GENERATED：由 result/ble_deployment.json 转出（61 枚坐标）
├── utils/
│   ├── beacon.js                       # 复用 fingerprint-collector 的扫描封装
│   ├── points.js                       # 标定点 CRUD（点位 ID/楼层/真值坐标/环境备注/标记方式）
│   ├── sampler.js                      # 采样会话：定长停留 + 逐信标中位数聚合（窗口与生产一致）
│   └── cstore.js                       # 会话存储 + 导出 JSON
└── pages/
    ├── index/                          # 仪表盘：标定点进度、参数摘要、入口
    ├── points/                         # 标定点列表/新增/编辑（真值坐标手输或从图纸拾取）
    ├── sample/                         # 核心：选点 → 开始采样（60–120s 倒计时）→ 实时信标表 → 保存一次
    └── export/                         # 复核 + 导出静态标定 JSON
```

### 4.2 采样口径（与生产链路保持一致，避免"标定一套、线上另一套"）

| 项 | 取值 | 依据 |
|---|---|---|
| 扫描方式 | `wx.startBeaconDiscovery` + `onBeaconUpdate` | 与生产客户端同源 |
| 聚合 | 2s 滑窗、逐信标 **RSSI 中位数**、截断 [-100,-20] | 与生产 `scan-window.ts` 一致 |
| 停留时长 | 60–120 s（可配） | `docs/24` §2 |
| 每次产出 | 每信标一条 `{beaconId, n, rssiMedian, rssiMin, rssiMax, rssiStd}` | 供回归与方差分析 |
| 重复 | 每点 3–5 次；至少覆盖人流高峰/低谷两个时段 | `docs/24` §2 |
| 距离真值 | 由**标定点真值坐标**与**台账信标坐标**算得 `d = |p_truth − b|` | 台账为唯一坐标源 |

> IMU：`docs/24` §2 提到"采集 BLE 快照 + IMU"。第一阶段 IMU **不参与解算**，故本工具将 IMU 采样
> 设计为**可选开关**（默认关），避免为未使用能力增加现场负担；如需留档，可开 `wx.startDeviceMotionListening`。

### 4.4 动态采集（复用主小程序，不新建工具）

在主小程序 `client/` 增加一个**标定模式开关**（设置页，写 kv，重启生效）：
- 开启后，定位/导航链路额外把每次可信估计写入本地 CSV/JSON 缓冲：
  `{ts, floorId, x, y, quality, confidence, 可见信标数, 当前指令序号, 会话状态}`；
- 步行结束后导出，与**真值路线**（图纸上按点采的真值坐标序列）在 PC 侧比对，得到：
  轨迹偏差、楼层切换时刻、偏航触发点、到达触发点（`docs/24` §6 动态测试表字段）。

> 该开关**只加记录，不改算法**，因此不影响生产行为；标定结束后可长期保留（便于每次参数变更复测）。

### 4.5 导出与回传

导出 `static_samples.json`（+ 可选动态记录 CSV）→ 经微信「分享文件」或开发者工具取出 →
放至仓库 `result/calibration/`（**该目录不提交仓库**，与 `result/*` 大文件策略一致；参数版本文件才入库）。

## 5. PC 侧拟合脚本：`src/tools/fit_location_params.py`

**输入**：`static_samples.json` + `result/ble_deployment.json`（信标坐标，用于重算真值距离）
**输出**：`result/calibration/location_params_<version>.json` + 控制台报告

### 5.1 回归模型（与生产公式同形）

对每个 (标定点, 信标) 观测对，`d` 已知、`rssi` 实测：

```
rssi = A − 10·n·log10(d)        ← 令 x = log10(d)、y = rssi，即为线性模型
      ⇒ 斜率 = −10n、截距 = A
```

普通最小二乘（`numpy.polyfit(x, y, 1)`）得 1m 参考 `A` 与指数 `n`；输出：
- 全楼统一参数（默认）；
- **分组参数**：按楼层、按遮挡类型（走廊/房间内/靠窗/金属区）分别拟合，并用 `docs/24` §4 的口径
  判断"全场共用 or 按信标分批"——判据：分组参数相对全局参数的误差改善是否显著（如分组后
  RMSE 下降 > 30% 且每组样本 ≥ 50 对）；
- 拟合质量：`R²`、RMSE、样本对数、各分组样本量。

### 5.2 阈值反推

- 用拟合参数重算每个静态点的估计坐标 → 得到**误差分布**，按 `confidence` 分组统计 **CEP50/75/90**；
- `RESIDUAL_RELIABLE_M` / `RESIDUAL_DEGRADED_M` 取「在该残差门限下，静态 CEP90 仍满足导航可接受误差」
  的最小值（`docs/24` §4「安全侧偏置：宁可多报 unreliable」）；
- `ORIGIN_MIN_CONFIDENCE` 同法反推。

### 5.4 参数注入（落地 `docs/24` 的"写入服务端配置并版本化"）

当前 `location_solver.py` 把这些参数写成模块常量，**无法配置化、也无法版本化**，与 spec 要求不符。需改为：

| 配置项 | 默认 | 说明 |
|---|---|---|
| `PATHAI_LOCATION_RSSI_AT_1M` | `-59`（标定前临时值） | 1m 参考 RSSI |
| `PATHAI_LOCATION_PATH_LOSS_N` | `2.0` | 路径损耗指数 |
| `PATHAI_LOCATION_RESIDUAL_RELIABLE_M` / `_DEGRADED_M` | `1.5` / `4.0` | 残差门限 |
| `PATHAI_LOCATION_PARAMS_VERSION` | `unset` | 参数版本号，写入日志与（可选）API 响应，便于追溯 |

> 同时修复语义：`BeaconEntry.txPower` 归还"发射功率（配置项）"语义，**不再参与测距**；
> 新增 `rssiAt1m`（缺省取配置默认值）。详见 `docs/27` §附录 A 与本次验证结论。

## 6. 冻结流程（与 `docs/24` §5 对齐）

```
① 图纸定真值点位（10–20 个）→ 录入标定小程序
② 静态采集（每点 3–5 次、跨时段）→ 导出 static_samples.json
③ PC 拟合 → 参数初值 + 报告
④ 写入配置（上表）→ 动态路线回归测试（复用主小程序标定模式）
⑤ 通过 → 冻结 paramsVersion，登记 docs/25 验收项与 spec DEC-002
⑥ 地图/信标变更 → 重跑本流程（docs/24 明确要求）
```

## 7. 测试策略（按 `docs/开发规范.md` §4）

| 层 | 用例 |
|---|---|
| 拟合脚本（pytest） | 合成数据反演：给定 `A=-69, n=2.31` 生成含噪观测 → 反演误差 < 0.5 dB / < 0.05；R² 与 RMSE 计算正确；分组判据（改善 30% 且样本 ≥50）边界；样本不足时报错而非静默出参 |
| 解算配置化（pytest） | 配置注入生效；缺省值回落；`paramsVersion` 出现在日志；**反例保护**：基准误设 -10 时必须判 `unreliable` 且不返回坐标（锁定 fail-safe 行为） |
| 标定小程序（jest，`utils/` 纯逻辑） | `sampler.js` 中位数/标准差/截断与生产 `scan-window.ts` 逐值一致；`truthDistanceM` 计算与 PC 侧一致（避免两端各算一套） |
| 数据约束 | 一律使用真实台账 61 枚与真实地图包；合成观测须由真实坐标反推（`docs/开发规范.md` §4） |

## 8. 风险与未决项

| 风险 / 未决 | 说明与建议 |
|---|---|
| 回归样本量 | 10–20 点 × 3–5 次 × 平均 3~6 枚可见信标 ≈ 数百对观测；**分组拟合可能样本不足** → 建议先只出全局参数，分组作为第二阶段 |
| 遮挡异质性 | 走廊 LOS 与房间内 NLOS 的 RSSI-d 关系不同；若全局拟合 R² 偏低，应引入**按遮挡分类的距离偏置**（`debug/trilateration_checker.py` 已有逐墙衰减原型可参考） |
| 真值坐标精度 | 图纸标注 + 激光测距，误差应 ≤0.2 m；建议每个标定点贴地面标记以便复测（`docs/24` §1） |
| 是否逐信标标定 | 建议**不逐枚**：61 枚 × 多距离采样在现场不可行；用"全局 + 分组"替代（`docs/24` §4 允许） |
| IMU 是否采集 | 第一阶段不参与解算，建议默认关闭（本文 §4.2） |
| 统计放在哪端 | 明确在 PC（可复算、可审计）；小程序只采原始数据。若坚持小程序出参数，需额外做双端一致性测试，收益低 |
| 与 `docs/27` 的顺序 | 现场一次出行建议：**先配置信标（写参数）→ 再标定参数（测 RSSI）**；否则测的是未配置/错配信标的信号 |
