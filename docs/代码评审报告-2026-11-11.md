## 一、总体结论（先行）

| 维度 | 评价 |
|---|---|
| 整体质量 | **高于同规模项目平均水平**，架构纪律性强，**未发现功能性假测试、未发现硬编码密钥** |
| 安全设计 | 成熟：opaque token 只存 SHA-256、openid 加盐哈希、admin HttpOnly+CSRF+审计、JCS+HMAC 配对协议均为教科书级 |
| **最大风险** | **1 个 P0**：服务端导航转向左右判定疑似颠倒（对视障用户是安全级缺陷）；**2 组 P1**：运维面接口零鉴权、小程序联调开关无护栏常开 |
| 服务端短板 | 可观测性缺失（未处理异常零日志）、请求体无大小上限、PG/MySQL 生产化缺口（并发保护/连接保活/令牌清理） |
| 客户端短板 | 失败后状态残留（导航冻结体/TTS 永久哑音）、pages 层几乎零测试、BLE 实扫适配层零测试 |
| 测试质量 | 双端断言密度高、mock 克制（只 mock 外部 I/O）；主要缺口是"安全门禁/网格重算/页面装配层"三类零覆盖 |

**发布前最低修复集（P0+P1，共 12 项）见第六节路线图。**

> **修复状态（2026-11-11）**：第一批 5 组问题已全部修复并通过全量回归（分支 `fix-review-batch1`）。因确认"客户端直连服务端、无反向代理"，原第二批的**请求体大小上限**提前完成（`BodySizeLimitMiddleware`，默认 10MB）。第二批其余项（鉴权复用 admin 会话、行锁、令牌清理、连接保活、扫描器缓存键、指纹库 site_id、BLE/pages 测试）待排期。

### 3.3 服务端架构优点（评审确认）

- 认证设计成熟：token 只存哈希、openid 不落明文、UNAUTHENTICATED/TOKEN_EXPIRED 语义区分；admin 全套 HttpOnly+SameSite=Strict+CSRF 恒时比较+审计
- 错误契约统一：全局 envelope + 稳定 code + requestId，客户端按 code 分支贯彻一致
- **幂等实现完整**（nav.py 唯一约束+IntegrityError 回滚复读，并发幂等正确——很多项目做错的地方）
- 配置与降级安全：demo 强制显式 DB URL、fake 微信仅限 local、指纹/LLM 失败降级不阻断主链路
- 配对协议（JCS 规范化+HMAC 域分离+常时比较+拒重复键）与定位解算（共面退化 MAP 软约束）数学正确
- 迁移 0001~0010 与 models.py 逐表核对一致
