# PathAI 室内导航系统 · 视障交互设计

> **视障模式是本系统的差异化重点，实现上需打破"地图中心"思维，重建以语音和触觉为主轴的交互。**

## 一、交互设计理念

视障模式不应只是"把地图换成语音"，而应当围绕安全、方向感和环境理解重新设计：

- **安全第一**：所有设计决策以视障用户能否独立安全通行为唯一评判标准
- **语音与震动为主轴**：不是附属，而是核心交互通道
- **低认知负担**：一次只做一件事，减少信息过载
- **冗余保障**：语音与震动互为冗余，嘈杂环境下也能感知

## 二、语音播报系统

### 2.1 分段式语音指引

避免一次性播报完整路线，只播报当前最需要的信息：

> "前方 12 米到达走廊交叉口。"
> "请向左转。"
> "左侧 3 米处是电梯入口。"
> "前方有扶梯，请保持右侧直行。"
> "您已进入大厅。"

每条指令应包含：

- 行进方向
- 距离
- 地标
- 风险提示
- 下一步动作

### 2.2 播报调度与优先级队列

系统维护一个优先级队列，确保高优先级安全提示能够打断当前播报：

| 优先级 | 类型 | 说明 | 打断行为 |
|--------|------|------|---------|
| 高 (safety) | 安全预警 | 楼梯、扶梯、玻璃门等危险提示 | 立即打断，重复播报两次 |
| 中 (medium) | 转弯指令 | 转弯、交叉口提示 | 打断后补播 |
| 低 (normal) | 常规提示 | 距离、方向确认 | 可被任意打断 |

### 2.3 TTS 合成与预录音频混合方案

**常规指令**（直行、距离、转弯）使用云端 TTS 实时合成，通过小程序 `wx.createInnerAudioContext` 或后台音频接口播放，合成延迟控制在 500 毫秒以内。

**安全关键指令**（楼梯预警、扶梯预警、玻璃门预警、到达目的地）使用预录音频包，提前下发到小程序本地缓存，触发时零延迟播放。

预录音频覆盖约 30 条高频安全指令，保证最关键的提示绝不延迟：

- "前方有楼梯，请停下"
- "前方有扶梯，请保持右侧"
- "前方是玻璃门，请小心"
- "您已到达目的地"
- "前方有障碍，请绕行"

### 2.4 指令长度控制

遵循认知负荷原则：

- 常规指令不超过 15 字（约 5 秒播报）
- 转弯指令不超过 20 字
- 安全预警指令不超过 10 字且重复两遍

AI 在生成时根据当前行进步速动态计算可用播报时间窗口，确保指令在用户到达下一个决策点前播完。

## 三、触觉反馈编码

### 3.1 震动语义编码

震动与语音互为冗余，保证嘈杂环境下仍能感知：

| 震动模式 | 语义 | 触发条件 |
|---------|------|---------|
| 单次短震 (100ms) | 即将转弯 | 距转弯点 5 米时 |
| 连续短震 × 3 | 到达交叉口 | 进入交叉口区域 |
| 单次长震 (800ms) | 需要停止 | 到达目的地或前方危险 |
| 持续低频震动 | 偏离路线 | 偏航超过阈值时 |
| 双次短震 | 电梯到达 | 电梯到达当前楼层 |

### 3.2 震动实现

通过 `wx.vibrateShort` 和 `wx.vibrateLong` 实现，连续震动通过定时器循环触发短震模拟。

### 3.3 震动与语音同步

震动与语音同时触发：

- 语音"请向左转"配合单次短震
- 语音"前方危险"配合长震动
- 语音"到达目的地"配合连续长震

## 四、手势交互设计

### 4.1 手势列表

| 手势 | 功能 | 说明 |
|------|------|------|
| 单指双击 | 重复上一条指令 | 任何界面位置 |
| 双指单击 | 暂停/继续播报 | 导航中界面 |
| 三指单击 | 请求协助 | 任何界面位置 |
| 长按 2 秒 | 返回首页/退出导航 | 任何界面位置 |
| 左右滑动 | 切换上/下一条指令 | 导航中界面 |

> **注意**：手势功能必须互斥、无重复绑定（早期版本中"单击"与"双指单击"同时绑定"暂停/继续播报"，属于设计冲突，已移除单击绑定，单击保留给按钮本身的确认/激活语义）。

### 4.2 与系统读屏的手势冲突处理

双指、三指等多指手势与 TalkBack/VoiceOver 的系统手势（如双指单击暂停朗读、三指滑动翻页）存在天然冲突。处理策略：

- 系统读屏开启时，自动禁用自定义多指手势，核心功能（重复指令、暂停、协助）改为大按钮 + 音量键/耳机按键触发
- 系统读屏关闭时（本系统自驱动语音通道的主场景），启用手势表中的自定义手势
- 手势模式切换时语音明确播报当前交互模式

### 4.3 手势实现

所有手势通过小程序 `bindtouchstart`/`bindtouchend` 自定义实现，记录触摸点数、时长和位移方向。

### 4.4 手势识别优化

- 支持单手操作：所有核心功能可通过单手完成
- 识别容错：增加手势识别的容差范围
- 手势反馈：手势识别成功后给出震动反馈

## 五、极简无障碍 UI

### 5.1 首页设计

布局为纵向单列大按钮，每个按钮高度至少 60px、宽度占满屏幕，间距 20px：

```
┌─────────────────────────┐
│   说出目的地            │  ← 语音输入入口
├─────────────────────────┤
│   常用地点              │  ← 上次导航地点快捷列表
├─────────────────────────┤
│   我在哪里              │  ← 播报当前位置
├─────────────────────────┤
│   呼叫协助              │  ← 长按触发
└─────────────────────────┘
```

核心按钮特点：

- 按钮内文字字号 20px 以上
- 高对比度配色（深底浅字）
- 支持系统 TalkBack/VoiceOver 读取
- 按钮可触达面积符合无障碍标准

### 5.2 导航中界面

更极简：全屏单区域，避免视障用户误触复杂控件。

```
┌─────────────────────────┐
│   请向前直行            │  ← 大字显示当前指令
├─────────────────────────┤
│   前方 12 米            │  ← 显示距离
├─────────────────────────┤
│                         │
│                         │
│      [重复指令]         │  ← 超大按钮
│                         │
└─────────────────────────┘
```

特点：

- 顶部大字显示当前指令
- 中部显示距离
- 底部一个超大"重复指令"按钮
- 导航中默认不显示地图，减少视觉干扰
- 如用户主动开启"地图辅助"选项，可在半屏显示简化地图供陪同人员查看

### 5.3 无障碍 UI 规范

| 规范项 | 要求 |
|--------|------|
| 按钮高度 | ≥ 60px |
| 按钮宽度 | 占满屏幕或 ≥ 80px |
| 文字字号 | ≥ 20px |
| 对比度 | ≥ 4.5:1 |
| 间距 | ≥ 20px |
| TalkBack 支持 | 100% 朗读覆盖率 |

## 六、预测性安全预判

### 6.1 提前预警机制

系统根据用户当前坐标、行进方向和步速，预测未来 5 秒内将接近的所有安全节点，提前将对应预警指令推入队列：

$$
\text{预测距离} = \text{步速} \times \text{预判时间} + \text{安全缓冲}
$$

视障用户步速约 0.8 米/秒，预判 5 秒即提前 4 米触发预警，加上 2 米安全缓冲，实际在距安全节点 6 米时开始准备播报。

### 6.2 抢占式播报

当高优先级安全指令进入队列时：

1. 打断当前播报
2. 在播报前插入一个短促提示音（如"叮"声）
3. 引起用户注意后再播报安全内容

这种设计模拟了导盲犬在危险前突然停步并轻拉牵引绳的行为模式。

### 6.3 危险静止策略

当用户行进方向正对高风险不可通行区域（如楼梯入口、玻璃幕墙）且距离小于 2 米时：

1. 触发连续长震动
2. 播报"请停下，前方危险"
3. 直到用户行进方向改变或定位确认用户已停止

### 6.4 高风险区域识别

系统需要识别并提醒以下高风险区域：

- 楼梯和扶梯入口（$r=10$）
- 玻璃门和玻璃幕墙（$r=5$）
- 旋转门（$r=5$）
- 湿滑地面（$r=3$）
- 施工围挡（$r=3$）
- 消防通道（$r=1$）
- 车辆出入口（$r=5$）
- 人流突然聚集区域（$r=3$）
- 自动门和闸机（$r=3$）

## 七、空间化提示

### 7.1 声道模拟

通过不同声道和声音方向模拟空间位置：

- 左侧提示音：目标或障碍在左侧
- 右侧提示音：目标或障碍在右侧
- 双声道提示音：目标位于正前方

### 7.2 声音方向编码

| 声音方向 | 编码方式 | 语义 |
|---------|---------|------|
| 左声道增强 | 左声道音量 > 右声道 | 目标在左侧 |
| 右声道增强 | 右声道音量 > 左声道 | 目标在右侧 |
| 双声道平衡 | 左右声道音量相等 | 目标在正前方 |
| 环绕音 | 模拟 360° 声场 | 目标在身后或特殊方位 |

## 八、环境描述功能

### 8.1 "我在哪里"功能升级

不只播报坐标和楼层，而是结合空间语义地图生成环境描述：

> "您现在在教学楼 2 楼走廊，左侧是 201 教室，右侧是电梯厅，前方 8 米是卫生间"

### 8.2 环境描述内容

环境描述包含以下信息：

- 当前位置的房间/区域名称
- 左右两侧的设施/房间
- 前方的设施/房间及距离
- 楼层和建筑信息
- 无障碍设施位置

### 8.3 描述生成策略

从空间语义地图中查询用户当前位置周边 10 米范围内的语义要素，按方向（前/后/左/右）分类整理，生成自然语言描述。

## 九、语音唤醒交互

### 9.1 唤醒词检测

唤醒词设为"小路小路"。**微信小程序不支持真正的后台常驻麦克风监听**，也不允许无用户交互的静默持续录音，因此唤醒方案必须按场景分级：

- **前台导航态**：通过 `wx.getRecorderManager` 的 `onFrameRecorded` 录音帧回调做本地轻量级关键词检测（KWS 模型），或接入"微信同声传译"插件的流式语音识别，实现免触唤醒
- **非导航态/后台态**：无法常驻监听，改用耳机按键、摇一摇（`wx.onAccelerometerChange`）或大按钮触发对话
- 持续录音需向用户明确提示"正在聆听"状态，符合微信小程序录音合规要求

### 9.2 对话交互

唤醒后进入对话态，用户说出请求，代理处理并播报响应：

- "小路小路" → 激活对话
- "带我去 101 教室" → 触发导航
- "我在哪里" → 环境描述
- "下一步怎么走" → 下一条指令
- "我需要帮助" → 协助请求

## 十、耳机交互适配

### 10.1 按键事件适配

很多视障用户使用蓝牙耳机，系统适配耳机按键事件：

| 耳机按键 | 功能 | 触发条件 |
|---------|------|---------|
| 单击 | 播放/暂停播报 | 导航中 |
| 双击 | 下一条指令 | 导航中 |
| 长按 | 请求协助 | 任何界面 |

通过小程序蓝牙 HID 或媒体按键事件监听实现。

### 10.2 耳机音频处理

- 支持蓝牙耳机音频输出
- 语音提示通过耳机播放，不干扰周围环境
- 支持左右声道独立输出，实现空间化提示
