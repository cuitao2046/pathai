## 三、关键技术决策与架构演进

### 解析器架构
- **图层策略**：PyMuPDF OCG 按层提取；`A-TECH-SANT` 整层显式剔除（get_drawings 不感知可见性）。
- **坐标标定**：`SCALE=0.0529 m/pt`、原点 `(2019.1,1154.8)pt`、Y 翻转、`set_rotation(0)` 处理 270° 旋转。
- **门识别四要素**：window 层摆弧（swing/fire）+ DK 矢量笔画（opening）+ 几何墙缝 + 贴墙判定；**DK 不在文本层、是 window 层矢量笔画**，旋转无关 4 方向。
- **房间识别**：OpenCV 栅格化 + 形态学 + 分水岭 + 标签探测；开放/封闭空间分治（垂直合并同类、共域多源测地分割、字号最大者为语义层）。
- **门归属权威判据**：门坐标贴墙房间（<0.6m），**不信任 `rooms` 字段**（geometry.doors rooms 漂移率 38%）。

- v9 节点 5 类（room/doorway/intersection/facility/facility_entrance），边带 distance/estimatedTime/accessibilityLevel/riskLevel。
- 开放空间（corridor/lobby/activity/atrium）不建封闭 room 节点，改建 intersection 节点；走廊连通性由 TI↔TI 承担。

## 四、工程纪律（铁律）

1. **铁律 0 — 禁止直接在 master 工作**（2026-08-09 起）：每项功能、优化或 bugfix 开始前均创建独立需求分支；改动前执行 `git branch --show-current` 确认当前不在 `master`。
2. **铁律 0b — 一分支一需求**（2026-08-10 起）：每个分支只承载一个功能/问题/文档需求；多个改动必须分别从合适基线创建分支，不得把无关改动、多个需求或其他分支的变更混用、顺手夹带在同一分支或提交中。同一需求的多笔提交须保持主题一致。
3. **铁律 — 分支名禁斜杠/反斜杠**（无条件）：沙箱 `.git/refs/heads/` 写带斜杠名静默失败 → unborn 分支 → `git add` 误全暂存；分支名一律使用连字符 `-`（如 `feature-xxx`）。
4. **铁律 — 合入后清理分支**：变更经人工校验并快进合入 `master`、推送成功后，先确认分支相对 `master` 无独有提交且无未保存改动，再删除该需求分支的本地分支（`git branch -d <branch>`）和远端分支（`git push origin --delete <branch>`），并执行 `git fetch --prune`；最终核验分支已清理、`master` 与远端一致、工作区干净。未合入或仍含独有改动的分支不得删除。清理范围仅限已确认完成的需求分支，不删除其他工具或会话管理的分支。
5. **铁律 — 完成必做两件事**：记录当日工作日志（append-only）+ push 到当前分支（沙箱无凭据时明确告知用户“待 push”）。
6. **门对象不做合并**（用户明确）：每个通过识别和有效性过滤的门对象独立保留，不按位置、距离、类型或几何相似度合并。
7. **骨架数据必须入库**：`result/skeleton_manual_parsed.json` 属代码，重生成必须 commit；严禁 `git checkout` 回退成旧版（曾导致渲染缺矩形）。
8. **编辑 `.gitignore` 后必须 `git add` 再 commit**，否则 merge 中静默丢失。
9. **push 凭据**：SSH 通道 `github-cuitao`（`~/.ssh/config` Host + `id_rsa_cuitao`）；remote 须用 `git@github-cuitao:cuitao2046/pathai.git`。重新 clone 后第一件事 `git remote set-url` 改回 SSH（https 需交互凭据、沙箱必败）。
10. **沙箱 git 禁忌**：禁 `git stash`（refs 写入失败 + index 搞乱）；fetch 后须 `git for-each-ref` 验证 refs 落盘；`git rm -f`/`git checkout -b` 在异常 index 上会误删文件，恢复用 `git archive <commit>`。
