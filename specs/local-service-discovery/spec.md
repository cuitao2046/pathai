## 1. 目标与成功条件

开发者在笔记本运行现有 PathAI Python 后端，手机微信小程序连接同一可互访局域网。笔记本和手机共同切换 Wi-Fi 或连接同一第三方手机热点，笔记本 IPv4 改变时，已配对的小程序能够重新找到并验证**同一安装实例**，无需手动修改编译期 IP 即可恢复允许重试的业务请求。不可恢复时，应暂停依赖服务端的安全指引，向用户给出可操作的检查项；不得将另一台同名服务当作原服务器。

成功依据为经指定真机、微信版本和网络环境验证的首次配对、发现、认证、读请求与受控写请求恢复；模拟器与单测通过不等于真机兼容性或发布达标。

## 2. 范围与边界

- **P0 可行性门槛：** 核查当前目标手机及基础库的 UDP 广播/单播、同网段 HTTP、系统权限、密码学依赖和热点客户端互访；不支持时记录阻塞，不以开发者工具关闭域名校验代替正式真机证据。
- **P0 真机测试入口：** 当前分支延续临时测试构建，只注册 `pages/p0-probe/p0-probe`，跳过登录预热，不加载地图或导航；v0.1.5 首次缓存 hardcode 地址仅作为待验证候选，在隔离页做无凭据 HTTP/UDP 并行预检。不开放进入地图或发起 PathAI 业务请求，探测结果不修改业务 API 地址或建立配对；正式导航首屏必须在完成后续可信业务接入或关闭测试构建时恢复。
- **P0 真机时序对照（已执行，未改善宿主热点场景）：** 针对 iPhone XS Max 热点宿主场景中 `onListening` 后的 UDP 异步错误，已将无凭据广播发送改为 `bind()` 后等待 `onListening` 再执行，保留有界超时及 socket 关闭。用户复测同一场景仍在监听/广播阶段收到无数字码的异步错误；不能据此断定原因或推广为普通 Wi-Fi/第三方热点失败。后续如需无凭据单播对照或改变错误诊断范围，先提出验证方案，不放宽防火墙至全部来源，不将探测 IP 接入业务。
- **P0 证据采集历史（0.1.4 已批准，后被 0.1.5 取代）：** 旧隔离页曾提供人工网络场景标签和脱敏摘要；按用户新决策，现行入口改为自动并行预检，不再人工选择 Wi-Fi 类型或要求逐拓扑取证。此前真机成功/失败记录保持原样，旧结果不得回填新一轮状态。
- **P0 安全随机数边界（0.1.4 已批准）：** 探测页只展示 `wx.getUserCryptoManager().getRandomValues` 在本次探测中取得期望长度随机字节的能力结论，不展示或持久化随机值。该结果不是 JCS/HMAC、密钥存储、服务身份验证或正式发布形态的可行性证明；这些仍须独立的维护库选型、跨语言向量和目标真机验证，未通过前禁止配对与业务请求。
- **寻址流程简化（0.1.5 已确认）：** 取消以普通 Wi-Fi A/B、第三方热点及热点宿主逐场景取证作为进入开发的条件；按“无缓存先写入 hardcode 地址候选 → 并发验证缓存地址与广播发现 → 缓存身份验证成功则忽略本轮广播结果 → 缓存失败则等待并验证发现候选 → 两条路径均失败才提示”实现。网络变化只触发同一流程的新轮次，不需要手动选择网络类型；不得把健康接口连通或未认证广播误判为已建立业务连接。
- **首次无缓存（0.1.5 已确认）：** 冷启动发现没有地址缓存时，把客户端 `client/config/env.ts` 的 `API_BASE_URL` 原值立即写入持久化候选缓存，保留协议、主机与端口；该默认值只提供首次地址来源，不是设备身份或当前网络可达性证明。已配对身份挑战通过后方能标记此地址为“最近已验证地址”并允许业务使用；若尚未配对或认证组件未就绪，P0 只能对缓存候选进行无凭据可达性检查，不能向其发送微信 code、Bearer、地图、位置或导航请求。
- **缓存与广播的并发裁决（0.1.5 已确认）：** 每轮同时开始已缓存地址的无凭据可达性检查、具备配对凭据时的身份挑战，以及针对同一 `deviceId` 的广播发现。旧地址身份验证成功即可进入就绪；发现分支的迟到结果只能被丢弃或关闭，不得覆写当前地址。旧地址失败后等待已有广播任务至有界截止时间，对来源、轮次、配对身份和挑战均验证通过的候选重新建立连接，成功才替换缓存。发现先失败不应在旧地址仍可用时弹窗。重入、切网与页面恢复均递增代次，旧轮次回调不得回写状态。探测接口 `/local/p0/probe` 与业务 `/healthz` 均只能证明可达性，不能证明设备身份。
- **失败与业务边界（0.1.5 已确认）：** 两条路径均失败或超时后弹出可读屏提示，告知检查服务、同网互访和防火墙，并提供重试/配对入口；不猜测网络拓扑根因。未验证身份前不得发送微信 code、Bearer、地图、位置或导航请求；导航中的连接失效按既有安全降级暂停旧指令。导航业务入口和地图 Range/数据 URL 只能在 P2 消息认证、明文风险与文件流边界评审通过后接入，P0 的 UDP OFFER 不能直接代替这些门槛。
- **P1 最小闭环：** 复用现有 Python 后端技术栈增加局域网发现服务、小程序配对/寻址/统一请求适配、网络切换恢复和扫码候选地址降级；保留现有 mock 模式，公网请求沿用原路径、协议与安全策略。对外连接前必须完成受控配对及挑战验证，不能以未认证原型替代。
- **P2 安全一致性：** 完成业务 JSON 请求/响应双向签名、防重放、撤销、读写响应身份校验，以及已接入写接口的操作幂等或结果未知处理；没有完成 P2 不宣称业务连接安全或真实导航可用。签名不提供局域网 HTTP 链路保密性。
- **P3 交付：** 本机管理入口、网络/防火墙排障、特定平台兼容清单和可追溯测试记录。首版 Windows＋手机微信；macOS、桌面微信与热点宿主手机不在首版支持承诺内。
- **不包含：** 系统 DNS、跨网段发现、NAT 穿透、公网注册中心、后台常驻发现、纯 IPv6、保证微信离线冷启动、直接把逻辑名交给 `wx.request`，以及重写现有业务后端为 Go。

本地寻址只负责**PathAI 后端地址**，不让现有讯飞 ASR/TTS 或微信登录变为离线服务。首次加载小程序、`wx.login` 与在线语音可能仍依赖公网，不能将“PathAI 业务局域网访问”表述为“完整导航离线可用”。

## 3. 产品对象及状态

| 对象 | 不变量 |
|---|---|
| 逻辑服务名 | 固定指向 PathAI 服务类别；存在同名服务器时必须绑定用户选定的设备。 |
| 设备身份 | 安装实例标识跨切网保持不变；不得由 IP、MAC 或可编辑显示名充当身份。 |
| 配对关系 | 每客户端独立、可撤销；已过期/被撤销时不提供业务连接，也不降级为免认证。 |
| 当前地址 | 只是短期候选；须由已配对身份验证后方可供业务使用。 |
| 网络代次 | 切网、主动切换设备或地址失效后递增；旧轮次回调不得覆盖当前地址。 |
| 未决写操作 | 以同一业务幂等键关联原操作；切网后不得换键盲目重放。 |

客户端连接态：`未配对 → 发现中 → 验证中 → 就绪 → 地址失效 → 发现中`；有限恢复失败进入`不可用`，被撤销进入`需重新配对`。`就绪`仅表示最近一次身份验证通过，不意味着后续网络必然可用。

## 4. 功能需求

### REQ-LSD-01 服务端发现与身份（P1）

- 启动既有业务 HTTP 服务并确认就绪后，才对目标局域网的有效发现查询返回响应；默认发现端口 39001，业务端口从实际运行配置取得，端口占用明确报错，不静默改用其他端口。
- 查询绑定逻辑服务名、请求轮次及可选的目标设备/配对记录。已配对响应绑定该轮次和配对关系并带可验证认证信息；未知、过期及已撤销的配对不应答。仅在管理员主动开启配对窗口期间允许展示**未认证候选**，不得据此放行业务。
- 仅接受有界、合法的数据报；对重复查询、来源和全局回复量限流，拒绝超长及畸形输入，避免开放式反射。服务端维护可用局域网接口，排除回环、虚拟/VPN/隧道接口，切网后更新有效接口；多网卡的入接口和回包来源必须实测，不做“通配监听自然正确”的假定。
- 设备身份在重启和切网后稳定，进程启动标识每次改变；设备私钥/配对密钥持久化受保护，不进入日志或版本库。管理员能看到本机就绪状态与所选局域网地址，不能通过局域网访问本机管理入口。

### REQ-LSD-02 首次配对与撤销（P1 配对；P2 撤销与完整持久化）

- 管理员在本机主动打开短期配对窗口，小程序扫描包含逻辑服务、设备身份、当前地址候选及独立高熵密钥的短期二维码；先认证当前地址，失败可搜索绑定目标设备的发现响应。二维码过期、取消或已使用后不能创建新配对。
- 激活须证明持有配对密钥且服务端记录为待激活；相同激活请求可重复读取同一结果，不创建第二条关系。未配对设备列表仅供展示，不获得 API 权限。
- 管理员可单独撤销客户端配对；客户端“忘记设备”只清理本地凭据，不冒充服务端撤销。配对凭据、二维码完整内容及认证头不得进入日志、诊断导出或剪贴板历史。
- 小程序本地存储不视为硬件安全区。密钥丢失或服务端设备身份文件重建时重新配对，不复用旧 IP 直接连接。

### REQ-LSD-03 小程序可信寻址（P1/P2）

- 小程序业务层只使用稳定逻辑服务名与受控相对路径；请求层负责解析当前地址，不接受完整 URL、协议相对 URL、任意端口跳转或未知地址重定向。
- 已配对时发现请求只寻找所选设备；客户端从应答实际来源获取候选 IPv4，校验私网地址、合法端口、协议版本、轮次、设备身份、配对 ID 及消息认证，并对候选 HTTP 地址做随机挑战验证；**挑战成功前不向候选地址发送 Bearer、微信 code、导航数据或其他业务请求**。
- 本地记住的旧 IP 只能作为待验证候选；TTL 过期、前台恢复或网络事件后重新验证；同一逻辑名下多设备不按响应先后自动切换。最多同时运行一个同设备恢复任务，候选、并发验证、等待队列及重试次数均有上限。
- 使用安全随机数、受维护且跨 Python/小程序一致的标准 JSON 规范化及 HMAC 实现；任何平台不能可靠实现时停止认证模式交付，不用 `Math.random` 或自制算法替代。

### REQ-LSD-04 切网、超时与安全降级（P1/P2）

- 监听网络变化并在小程序每次回前台时检查地址；即使前后都报告 `wifi`，请求连接错误仍须触发地址失效与新轮次发现。旧轮次回包、超时回调与旧地址的成功响应不得把连接状态改回旧网络。
- 恢复预算、轮次、单候选验证和普通请求超时采用有界默认值，初始参考分别为 12 秒、3 轮、1.5 秒与 5 秒；仅安全读取或已证明幂等的写请求最多自动重试一次。预算耗尽停止自动重试，支持用户手动重试。
- 服务不可达、身份错误或配对撤销时，不继续播报旧导航方向指令、不伪造位置、不得把新服务误当旧会话。连接恢复后仍须按既有 `REQ-SESSION` 重查导航会话、地图版本、权限和定位新鲜度。
- 区分“有明确证据的权限拒绝/身份错误/撤销/协议不兼容”和“原因未知的发现或连接失败”；后者提示检查同网、服务启动、局域网互访与防火墙，不猜测原因。

### REQ-LSD-05 地址二维码降级（P1/P2）

- 广播不可用但 HTTP 单播可达时，服务器展示仅包含设备身份及当前局域网地址的**地址二维码**，不含配对密钥；已配对小程序扫码后仍须挑战验证，未配对须先走配对流程。
- 若 UDP 与 HTTP 均被隔离，扫码不能解锁连接；明确提示换用可互访网络。手输 IP/桌面微信首次配对非首版承诺，需另行评审入口及安全引导。

### REQ-LSD-06 现有请求与业务保持（P1/P2）

- 现有微信登录、Bearer token、会话归属、地图 ETag/分片下载、定位/导航序号与讯飞 URL 签发不因寻址改造而移除。进入已评审的本地模式时，所有指向 PathAI 服务的请求与地图数据下载使用同一**已验证**设备/地址；不得保留另一个固定 `API_BASE_URL` 绕过寻址。
- **局域网与公网分界：** 对局域网内经配对验证的 PathAI 后端地址使用 HTTP，不强制改成 HTTPS；公网请求、既有讯飞 WSS 及其域名要求均不受本方案影响。局域网 HTTP 即使带签名也可被同网旁观者读取，可能暴露微信 code、Bearer、识别文本、签名 URL 与位置/轨迹；切换网络时不得静默把公网请求改送局域网或反之。真实用户数据和公开交付的安全/隐私准入需另行评审这一剩余风险，未获准前仅在受控可信网络使用测试身份与非敏感数据；不能宣称等同于现有 `REQ-PRIVACY` 的 HTTPS 保护。
- 协议认证不替代现有 Bearer 授权。业务请求、响应及配对绑定通过消息认证验证后再交现有业务解析；未经签名、时间窗口错误、nonce 重放、状态码或响应正文被篡改必须拒绝。地图包字节下载/Range、现有 WebSocket 与文件流不在 v1 JSON 双向签名契约内，须定义独立的验证或豁免边界，**未评审前不得把其 HTTP 数据下载视为已受传输认证**。[待确认]
- 对所有现有写端点逐一登记副作用与重试资格；未证明幂等或未有操作状态查询能力时，对网络失联后的未知执行结果显示“待确认”，不得自动重新提交。原有创建导航会话幂等键保持同一次操作不变。

### REQ-LSD-07 用户反馈与运维诊断（P1/P3）

- 设置页显示连接模式、选定设备、状态及可访问的重试/扫码/忘记设备入口；连接不可用时提供震动及可读屏文本，不用颜色作为唯一提示。管理端仅本机显示接口、当前地址、发现端口与配对/撤销状态。
- 脱敏记录发现、验证、恢复阶段与错误分类，绝不记录密钥、二维码、Bearer、原始请求体、完整轨迹或认证头；日志大小和保留期有上限。提示及日志不得将“热点隔离”这种推测说成已证实根因。

## 5. 协议与边界约束（待冻结）

- 以来源方案 v1 的 UDP `DISCOVER`/`OFFER` 字段、1200 字节上限、39001 端口、轮次去重与限流值为候选契约；IP 以 UDP 来源为准，**应答 IP 仍需 HTTP 挑战验证**。
- 来源方案的签名域分离、RFC 8785 JCS、HMAC-SHA256、无填充 Base64URL、128 位挑战/nonce、256 位独立配对密钥及请求/响应原始字节摘要为候选安全基线；必须补齐跨语言测试向量和畸形输入拒绝规则后冻结。
- 来源方案将 JSON HTTP 请求签名绑定 `pairId`、`bootId`、时间、nonce、HTTP 方法、实际路径/查询及原始请求体摘要，响应绑定原请求 nonce、状态码与原始响应体摘要；时间与 nonce 双重约束，进程重启后旧 `bootId` 失效。不能将“认证”表述为“加密”。
- 对既有大地图 Range 响应、未登录的微信换码、管理后台 cookie 流和在线语音凭据签发分别做威胁与接入评审；P0 仅做无凭据隔离原型，完整业务接入待 P2 消息认证、数据流边界及既有规格对齐后执行。局域网 HTTP 明文残余风险不得用消息认证测试通过来掩盖。

### P1 隔离闭环契约草案（0.1.6，待评审）

- **范围：** 本轮仅开发本机主动配对、已配对 UDP OFFER、业务 HTTP 端口的无业务数据身份挑战，以及隔离页上的缓存优先/发现回退与地址二维码候选。即使挑战通过，也只建立隔离态的已验证地址记录；保持 P0/隔离首屏，不向该地址发送微信 code、Bearer、地图、位置或导航请求。P2 完成前不把当前业务请求栈切换到动态地址。
- **配对材料：** 管理员通过仅回环可达的管理入口开启 120 秒窗口；每次生成独立 256 位随机密钥与 `pairId`，二维码文本格式、字段及地址范围沿来源方案 §10.2。配对密钥仅能通过本机展示的二维码交付；激活须证明持钥，待激活窗口到期或取消即失效，同一激活操作重复提交不得产生第二条配对。每个已激活客户端可独立撤销；客户端忘记设备不等于服务端撤销。密钥不写入日志、仓库或普通诊断导出，小程序 storage 不作为硬件安全区。
- **认证格式：** 采用受维护且适配 Python/微信小程序的 RFC 8785 JCS 与 HMAC-SHA256 实现；`OFFER` 的域前缀为 `LSD-OFFER-V1\n`，挑战响应为 `LSD-PROBE-V1\n`，输入为去掉 `auth` 的对象经 JCS 编码后的 UTF-8 字节；标签无填充 Base64URL，验证用常量时间比较。固定协议版本、字段类型/长度、唯一 JSON 键、128 位安全随机 `requestId`/挑战、256 位独立配对密钥；非法 JSON、重复键、超长与额外危险字段拒绝而非宽松解释。库选择、打包与跨语言拒绝向量须在编码前核实；真机密码能力未通过不宣称认证可用。
- **地址认证：** 已配对发现只对匹配 `deviceId`/`pairId` 的有效请求应答；应答绑定 `requestId`、进程 `bootId`、实际业务端口与配对签名，来源 IP 为候选且须为 RFC1918 私网地址。客户端验证 OFFER 后仍必须向候选业务端口发送一次性随机挑战，核对响应签名、同一设备、配对、挑战、`bootId`、协议版本和就绪状态；旧轮次、旧启动实例、撤销/过期关系及 1500 ms 之外的响应一律不得置为已验证。二维码地址同样只作候选，不能绕过挑战。
- **缓存与时序：** 无缓存先写 hardcode `API_BASE_URL` 为未验证候选；每轮同时验证缓存候选与开启已配对发现，缓存挑战成功时放弃本轮发现结果，缓存失败后等待发现并逐一挑战有界候选。仅当前网络代次内成功的挑战可原子更新 `serviceName + deviceId` 的最近已验证地址；持久化地址冷启动仍降为候选。回前台、切网、地址错误触发新代次；同一设备仅一个恢复任务，不重用迟到回调。两路均失败只提示重试/扫码或重新配对，不回退无认证业务访问。
- **后端界限：** 使用现有 Python/FastAPI 业务端口提供身份挑战与激活；管理入口不得挂到对局域网监听的现有 `/admin` 页面。发现服务只有业务 HTTP 确认就绪后应答，独立 P0 端口 `39002` 不得冒充业务端口。UDP 有报文上限、私网来源检查、逐源与全局限流、多网卡来源核验和明确端口占用失败；网卡与防火墙范围必须按目标 Windows 环境验证，不因单测通过承诺任意网络。
- **门槛：** 先补 Python/小程序跨语言成功及失败向量、重复键/重放/冒名/撤销/迟到/容量上限测试，再完成目标真机且关闭调试绕过的配对—挑战闭环。身份认证不提供 HTTP 加密；真实用户数据、业务统一接入、地图 Range 与写操作均继续受 P2 和安全/隐私评审阻断。
- **本轮实现边界（2026-11-01）：** 地址二维码为本机受保护管理接口返回的 `kind=local-service-address` JSON，包含 `version=1`、`serviceName`、`deviceId` 及私网 `endpointHint`，不含配对密钥；客户端仅在设备标识与当前配对一致且 HTTP 随机挑战通过后缓存地址。缓存键按设备与配对关系隔离；缓存路径允许服务重启产生新 `bootId`，发现路径必须与本轮 OFFER 的 `bootId` 相同。当前仅隔离页显示身份验证结果，实际网络监听端口绑定、多网卡真实性、密钥存储保护及正式真机验证未完成，不开放业务 API。
- **小程序依赖交付修复（2026-11-01）：** 微信 npm 构建对 `@noble/hashes` 仅产出不允许直接调用的根入口，不能解析 HMAC/SHA-256 子路径。保持固定版本的受维护 `canonicalize` 与 `@noble/hashes`，以浏览器目标构建单个自包含 CommonJS 模块随小程序源码交付；自动化须校验产物无外部 `require` 且签名向量与后端一致。构建成功只证明本地包可加载，仍须模拟器冷启动和目标真机确认，不因依赖打包调整放宽配对或业务安全门槛。

### P1 免配对 IP 发现（v0.1.7 已批准的隔离替代范围）

- **动机及取舍：** 用户批准隔离页直接发现服务端 IP。本轮不展示配对二维码、不激活配对或调用签名挑战；局域网同网仅作为可达性前提，**不构成设备身份认证、内容防篡改或保密证明**。上文配对条款为旧版原型，不适用于本轮隔离入口。
- **本轮 P1 隔离行为：** 继续只在隔离页运行。无缓存时先保存 hardcode `API_BASE_URL` 私网地址作为候选；每轮并发执行缓存候选的无凭据业务端口健康检查和有界 UDP 广播。缓存健康检查成功即显示可达并忽略广播结果；失败才等待发现应答，对应答来源 IPv4、协议版本、`requestId`、有效业务端口与私网范围做格式和轮次校验，再经**业务端口**的无凭据健康检查确认后保存地址候选。不得把 P0 探测端口 39002 的成功冒充为业务端口 8000 可用；任一路失败均不因另一支仍在进行而过早弹窗，两路均失败才提示重试及同网互访检查。旧轮次结果不可覆盖新一轮缓存。
- **本轮服务端：** 本地模式默认发现端口 39001、业务端口 8000，其他环境默认关闭，可显式覆盖；业务服务随进程启动后响应有界、限流的无配对查询，端口必须与实际 HTTP 监听一致，端口占用明确失败。旧配对接口保持禁用，历史持久化记录和密码模块暂留，不参与本轮链路；P0 诊断应答不能混作业务地址。多网卡的真实入接口/掩码、正式微信域名规则仍待真机核验。
- **业务安全边界：** 免配对广播和 `/healthz` 只证明“某个私网主机响应”，不保证它是预期 PathAI 安装实例；同网攻击者可伪造服务并接收微信 code、Bearer、位置、轨迹等数据。**本轮仅允许隔离页显示与缓存无凭据候选；严禁凭无配对发现结果直接切换登录、地图、导航、语音凭据签发或任何业务请求地址。** 若要让导航实际使用发现的 IP，必须另行评审可信服务身份与局域网 HTTP 明文隐私风险，或明确放弃身份保证并取得相应安全/隐私批准；不能以“局域网”替代此项决定。
- **本轮验收：** 以真实目标机复测无缓存、缓存命中、缓存失败发现成功、发现失败缓存成功、双路失败、服务重启与新旧轮次；负面用例覆盖畸形/超长 UDP、过期应答、端口不符、非私网来源、同名伪服务不被标记为可信。前端移除“配对/已验证身份”文案；目标真机及正式微信域名策略的限制须据实报告。

### P2 动态 IP 承载导航业务提案（v0.1.9 草案，待安全/产品评审）

- **目标与待决前提：** 用户要求让动态 IP 承载导航业务。本节仅为实施前规格，不撤销 v0.1.7 的“未认证候选不得承载凭据”限制。必须先选定并验证服务身份和传输保密策略：优先使用有可验证服务器身份的 HTTPS/TLS（小程序正式域名、证书和 IP 变化适配均须真机验证）；如继续局域网 HTTP，须明确可信受控网络、可处理的数据敏感等级、微信 code/Bearer/位置/语义文本及讯飞签名 URL 的明文暴露和伪服务风险，并经安全/隐私准入批准。若无可验证身份且无明确风险准入，仅允许继续隔离页，不能把无配对 UDP OFFER 或 `/healthz` 视为可信身份。
- **统一寻址：** 客户端在任何 `wx.login` 换码、Bearer、地图摘要与分片、定位、导航及讯飞凭据签发之前，必须先取得**获准的服务地址**；未通过时维持隔离/安全暂停，不退回未经验证的 hardcode 或最后缓存 IP。统一地址源由单一装配器向令牌管理器、ApiClient、MapService 和语音凭据请求提供；原有 mock 数据源与讯飞 WSS 域名不改。`opts.url`、地图 `dataUrl`、重定向与调试重写须限制同一已获准源，禁止向其他私网/公网主机附带 Bearer；地图摘要来源与 Range 字节还须有可验证内容及同一地图版本边界。
- **恢复与重放：** 冷启动、回前台、切网及请求连接失败触发同一有界恢复任务；地址失效立即阻断新凭据发送及过期导航播报，旧轮次结果不能覆盖新地址。先验证新地址，再校验 Bearer 所属主体、服务端导航会话、地图版本及定位新鲜度，符合 `REQ-SESSION` 才恢复导航。GET/安全读取仅在明确同源授权后有限重试；POST/更新类写操作对执行结果未知时不得换地址换幂等键盲重发，先查询状态或显示待确认。
- **地图与隐私门槛：** 地图摘要 `dataUrl` 的绝对 URL 及本地重写须被单一地址策略约束；Range/206/304/416、ETag/dataSha256、断点续传与异步更新维持既有契约。若依赖 HTTP 消息签名，只能保证签名覆盖的 JSON 请求/响应完整性，不能提供保密性；地图字节流及响应身份另需明确保护方式。须同时更新 `specs/phase-1-indoor-navigation/spec.md` 的 `REQ-PRIVACY` 与决策记录，得到安全/隐私评审结论前仅限隔离验证，不恢复导航首屏。
- **实施阶段与验收：** (A) 冻结身份和传输选择、真机合法域名/证书/网络策略；(B) 实现可注入的单一地址解析器与错误边界，单测验证登录/地图/导航同源及恶意绝对 URL 拒绝，仍以假 transport 和测试身份隔离；(C) 仅在 A/B 与第一阶段隐私规格对齐后恢复地图首页、全业务接入，并覆盖断网、变 IP、缓存污染、同网伪服务、地图 Range、重复写、会话新鲜度和无障碍降级。无真实手机证据不得宣称导航可用。
- **方案 2 安全准入测试记录（2026-11-01，结论：不通过）：** 用户选择受控局域网 HTTP，并要求先做安全准入测试；选择方案不等于接受可被同网冒名/旁观的真实凭据和位置泄露。现有免配对 OFFER 标记 `authenticated=false`，`/healthz` 只检验可达性；无法拒绝返回同样响应的同网伪服务。客户端 `ApiClient.send` 在判断 `opts.url` 是否同源之前取得令牌并附加 Bearer，且没有同源/跳转拒绝；`MapService.dataUrlFor` 可以采用异源 `dataUrl` 或固定 `API_BASE_URL` 重写，完整文件 SHA-256 不证明摘要的服务器身份。令牌换码、讯飞签发、位置与轨迹沿 HTTP 均无保密性；401 对 POST 一律重登重放，切地址时未知执行结果的写请求缺少安全处置。第一阶段 `REQ-PRIVACY` 仅允许已配对且通过挑战的受控 HTTP 测试身份，本方案尚未满足，`REQ-MAP` 仍要求 HTTPS 数据地址。
- **测试证据与边界：** 客户端 `npx tsc --noEmit` 成功，Jest 304 通过/1 跳过；从仓库根分别执行根测试 140 通过/1062 subtests、后端测试通过。默认 `python -m pytest -q` 因本机同名 `tests` 包冲突收集失败，根目录 `pytest` 不在 PATH；拆分测试并显式置前导入路径后均通过。这些功能回归不替代伪服务、网络嗅探、异源凭据与微信真机重定向的拒绝性测试；当前仅隔离页无凭据发现为可继续验证范围，导航业务**不准入**。
- **解除阻断前的最小负面验收：** 在假 transport 下证明未认证 OFFER、伪造 `/healthz`、缓存投毒、旧轮次、异源 `opts.url`/`dataUrl`/重定向均不会使微信 code、Bearer、Range 或位置数据外发；写请求已执行但响应丢失时不得盲重试。网络侧仅能用测试身份与非敏感数据核对受控 Wi-Fi 的旁观者可见性，且必须明确实际风险接受主体、网络边界、凭据数据范围和清理方式；即便负面测试通过，纯 HTTP 也不能证明保密，缺少服务身份和第一阶段规格批准仍不可接入真实导航。

### 正式业务接入：免配对局域网 HTTP（v0.2.0，2026-11-01 用户确认）

- **用户确认范围：** 不做设备配对与身份挑战；UDP 广播发现并经业务端口 `/healthz` 可达检查的私网 IP 直接作为客户端业务根地址。登录换码、Bearer 业务请求、地图摘要与 Range 下载、定位、导航及讯飞凭据签发统一使用该地址；恢复 `pages/map/map` 为首屏，实现“启动自动发现 → 加载地图 → 导航可用”。
- **风险归属：** 用户明确要求本阶段不再考虑安全准入（本轮原话“不用考虑安全问题，现在可以直接接入正式业务逻辑”）。由此形成的可用行为属**用户接受的开发/演示期例外**：免配对 OFFER 与 `/healthz` 不证明服务器身份，HTTP 不提供链路保密，同网伪服务或旁观者可取得微信 code、Bearer、位置与轨迹。界面与日志只能表述“已发现并连接局域网服务”，不得声称“身份已验证”“加密传输”或“安全接入”。
- **生效边界：** 例外仅用于本地/自建服务与受控联调网络。真实用户上线或公网部署仍须按 P2 提案补齐 HTTPS 与可信证书；届时恢复身份与传输门槛，不在 HTTP 上承载真实用户位置数据。
- **实现约束：** 单一地址来源（`services/service-endpoint.ts`）在启动时完成解析，供令牌管理器、`ApiClient`、`MapService` 与语音凭据请求共同读取；解析失败不静默回退旧 IP，地图页显示可复读错误并允许重试。地址解析结果持久化复用既有 `discovery:p0-candidate-url` 缓存键。

## 6. 验收场景（待执行）

1. 指定 Android/iOS 真机对 UDP 广播、单播及同网段 HTTP 分开验证，并记录基础库、微信/系统版本与热点拓扑；失败必须保留失败结论。
2. 管理员开启窗口 → 扫码 → 认证 → 本地无凭据原型探测成功；P2 与受控测试范围冻结后，使用测试身份完成现有业务请求；过期二维码和撤销配对不能取得业务权限。
3. Wi-Fi A 切换 Wi-Fi B 或第三方手机热点，后端 IP 变化后连接同一 `deviceId`；同名服务器、旧 IP 伪服务、迟到旧轮次均不得串连。
4. 广播阻断但单播可达时，扫码地址经挑战后恢复；UDP 与 TCP 均隔离时有界失败且不伪称扫码可解。
5. 切网时并发读请求只运行一个恢复任务；写请求响应丢失时不能重复产生副作用，未具备幂等保证时给出结果未知状态。
6. nonce 重放、认证响应体/状态码篡改、超长/重复键 JSON、洪泛输入均按协议拒绝，日志无敏感数据。
7. 小程序回前台后先恢复可信地址，再执行原有会话、地图和定位校验；服务不可达期间不播报旧转向指令。
8. 分别检查地图摘要与数据下载、微信登录、在线语音、管理后台既有链路；明确标注哪些链路经消息认证、哪些仍为 HTTP 明文、哪些继续走公网，不夸大“完整离线”或“链路加密”。

## 7. 与现有规格的关系

- 当前 `specs/phase-1-indoor-navigation/spec.md` §6 `REQ-BOOT`/`REQ-SESSION`、§6 `REQ-PRIVACY`、§7 API 摘要仍有效；v0.2.0 用户确认的局域网 HTTP 例外已在 `REQ-PRIVACY` 追加条款说明（仅联调/自建服务，真实用户与公网仍须 HTTPS）。两份规格不得各说各话，后续若改变生效边界须两份同步更新。
- `docs/25-第二阶段真机联调检查清单.md` 当前对局域网 IP 及调试绕过的描述只能作为现状，确认方案后增加关闭开发工具绕过的真机可行性测试与安全准入，不得将当前调试配置描述为正式可用。
- P0 原型最初在独立 worktree 中开发；该工作区的改动已按用户后续要求快进合入 `master`，当前仅使用 `D:\code\pathai` 工作区。此工作区变化不改变 P0 隔离探测、不向未认证地址发送业务凭据及 P1/P2 安全门槛。

## 8. 决策记录

### 已确认决策

1. **服务形态（2026-11-01 用户确认）：** 复用现有后端技术栈，不重写为 Go；局域网发现服务与原 Python/FastAPI 业务服务协作。
2. **模式范围（2026-11-01 用户确认）：** 局域网请求保持 HTTP，公网请求不受本方案影响；不把 HMAC 身份认证误称为传输加密。真实用户数据与发布前的剩余风险仍需安全评审。
3. **首版平台（2026-11-01 用户确认）：** Windows＋手机微信；macOS/桌面微信后置。
4. **业务覆盖（2026-11-01 用户确认）：** 全部现有 PathAI 小程序调用统一接入已验证的局域网地址，地图 Range/非 JSON 数据认证边界须单独冻结，讯飞公网链路不改。
5. **实施门槛（2026-11-01 用户确认）：** 先做 P0 真机 UDP、局域网 HTTP 和密码能力验证；不通过不宣称自动发现，P2 安全一致性未通过不宣称完整业务安全。
6. **工作区处理（2026-11-01 用户确认）：** 使用新分支开发，保留当前已有未提交改动所在的工作区不动；通过独立 worktree/副本隔离新分支。
7. **P0 真机入口（2026-11-01 用户确认）：** 新分支临时使用独立隔离探测首屏并跳过业务预热，避免向旧固定 IP 发送微信 code、Bearer 或地图/导航数据；P0 不改变正式业务地址。
8. **工作区归并（2026-11-01 用户确认）：** 将 `feature-localdns` 快进合入本地 `master` 工作区，移除独立 worktree 与已合并分支；当前 `master` 暂时仍是 P0 探测专用构建，未恢复正式导航首屏。
9. **P0 UDP 时序对照（2026-11-01 用户确认并复测）：** 第三轮真机报告显示 `onListening` 后异步错误，但原实现 `bind()` 后立即 `send()`，不能凭错误发生阶段推断发送时已就绪。现仅在 `onListening` 后发送一次，超时或错误后不再发送；iPhone XS Max 热点宿主场景复测仍异步报错，普通同网 Wi-Fi 的无凭据 UDP→HTTP 闭环成功，不能据此断言热点失败根因或 P0 整体可行性。
10. **P0 真机证据页（2026-11-01 用户批准）：** 按 §2 实现手动场景与不持久化的脱敏摘要；客户端单测只能验证展示和旧结果不回填，第二 Wi-Fi、第三方热点及无调试绕过形态仍须真机取证。
11. **首次缓存来源及成功判据（2026-11-01 用户确认）：** 缓存缺失时先将 hardcode `API_BASE_URL` 写成待验证地址候选；缓存地址只有已配对设备身份挑战通过才算连接成功。按 §2 的缓存优先/并行广播裁决执行，不因 `/healthz` 或 P0 HTTP 返回 200 放行业务凭据；取消按不同 Wi-Fi 场景逐一验收。
12. **P1 隔离实现（2026-11-01 用户继续推进）：** 先实现并测试配对、签名 OFFER、挑战和地址码候选；不把已验证地址接入业务请求栈。管理面、真实网卡/端口、密钥保护与发布形态真机仍须独立验收；不能将开发版测试成功标记为 P1 完成交付。
13. **正式动态地址业务接入（2026-11-01 用户最终确认）：** 免配对、局域网 HTTP，广播发现的私网 IP 直接承载正式导航业务；用户明确表示不再考虑安全准入。该确认以 §5“正式业务接入：免配对局域网 HTTP（v0.2.0）”为准，属开发/演示期例外，不覆盖真实用户上线与公网 HTTPS 要求。

### 当前隔离实施决策

- **免配对变更（2026-11-01 用户批准 v0.1.7 隔离范围）：** 不进行设备配对，隔离页直接发现服务端 IP；上述配对身份认证条款为旧版历史，不作本轮验收依据。功能流程与安全限制见 §5“P1 免配对 IP 发现”；业务接入须独立评审。
- **P2 方向（2026-11-01 用户提出，v0.1.9 待评审）：** 希望动态 IP 承载导航业务；需先确认服务身份和传输/隐私准入，再按 §5“P2 动态 IP 承载导航业务提案”分阶段实施。此项需求不自动授权把未经认证候选传给业务栈。

### 待确认提案

- P1 隔离实现仍待安全与真机评审：管理入口仅靠应用层回环及令牌限制、配对密钥在业务数据库中可还原、UDP 网卡/实际服务端口未经目标机证明；这些门槛未解除不得转为可信业务寻址。P0 页面退出及业务连接仍待 P2 独立确认。
- 局域网 HTTP 与既有 HTTPS 规格的对齐及真实数据安全准入属实施前冻结项，不伪称已获得发布许可。

### 模块实现前冻结项

- 基础库下限、目标机型/微信版本、网段/热点设备、UDP 广播及本地 HTTP 在**关闭调试绕过**时的实测可行性；不通过时保留扫码单播或重新评估客户端形态。
- 同源业务 HTTP 与既有 HTTPS 规格的文本对齐、可处理的数据敏感等级、微信登录/语音公网依赖边界、密钥存储及设备撤销策略；真实用户数据的明文风险另行审查。
- HTTP JSON 消息签名、地图 Range 字节流、配对探测和操作结果查询的跨语言契约及安全测试向量；现有业务端点逐一分类可重试资格。
- 本地后端服务发现的独立进程/同进程生命周期、本机管理端口、持久化身份目录、Windows 防火墙策略与多网卡限制。
