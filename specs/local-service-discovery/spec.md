## 1. 目标与成功条件

开发者在笔记本运行现有 PathAI Python 后端，手机微信小程序连接同一可互访局域网。笔记本和手机共同切换 Wi-Fi 或连接同一第三方手机热点，笔记本 IPv4 改变时，已配对的小程序能够重新找到并验证**同一安装实例**，无需手动修改编译期 IP 即可恢复允许重试的业务请求。不可恢复时，应暂停依赖服务端的安全指引，向用户给出可操作的检查项；不得将另一台同名服务当作原服务器。

成功依据为经指定真机、微信版本和网络环境验证的首次配对、发现、认证、读请求与受控写请求恢复；模拟器与单测通过不等于真机兼容性或发布达标。

## 2. 范围与边界

- **P0 可行性门槛：** 核查当前目标手机及基础库的 UDP 广播/单播、同网段 HTTP、系统权限、密码学依赖和热点客户端互访；不支持时记录阻塞，不以开发者工具关闭域名校验代替正式真机证据。
- **P0 真机测试入口：** 当前 `master` 的临时测试构建只注册 `pages/p0-probe/p0-probe`，跳过 `onLaunch` 的登录预热、不加载地图或设置页业务自检；仅展示隔离探测入口与结果，不开放进入地图或发起 PathAI 业务请求的入口。探测完成后不修改业务 API 地址、不缓存候选地址，也不建立配对；正式导航首屏必须在完成后续可信业务接入或关闭测试构建时恢复。
- **P0 真机时序对照（已执行，未改善宿主热点场景）：** 针对 iPhone XS Max 热点宿主场景中 `onListening` 后的 UDP 异步错误，已将无凭据广播发送改为 `bind()` 后等待 `onListening` 再执行，保留有界超时及 socket 关闭。用户复测同一场景仍在监听/广播阶段收到无数字码的异步错误；不能据此断定原因或推广为普通 Wi-Fi/第三方热点失败。后续如需无凭据单播对照或改变错误诊断范围，先提出验证方案，不放宽防火墙至全部来源，不将探测 IP 接入业务。
- **P1 最小闭环：** 复用现有 Python 后端技术栈增加局域网发现服务、小程序配对/寻址/统一请求适配、网络切换恢复和扫码候选地址降级；保留现有 mock 模式，公网请求沿用原路径、协议与安全策略。对外连接前必须完成受控配对及挑战验证，不能以未认证原型替代。
- **P2 安全一致性：** 完成业务 JSON 请求/响应双向签名、防重放、撤销、读写响应身份校验，以及已接入写接口的操作幂等或结果未知处理；没有完成 P2 不宣称业务连接安全或真实导航可用。签名不提供局域网 HTTP 链路保密性。
- **P3 交付：** 本机管理入口、网络/防火墙排障、特定平台兼容清单和可追溯测试记录。首版 Windows＋手机微信；macOS、桌面微信与热点宿主手机不在首版支持承诺内。
- **不包含：** 系统 DNS、跨网段发现、NAT 穿透、公网注册中心、后台常驻发现、纯 IPv6、保证微信离线冷启动、直接把逻辑名交给 `wx.request`，以及重写现有业务后端为 Go。

本地寻址只负责**PathAI 后端地址**，不让现有讯飞 ASR/TTS 或微信登录变为离线服务。首次加载小程序、`wx.login` 与在线语音可能仍依赖公网，不能将“PathAI 业务局域网访问”表述为“完整导航离线可用”。

## 3. 产品对象及状态

| 对象 | 不变量 |
|---|---|
| 逻辑服务名 | 固定指向 PathAI 服务类别；存在同名服务器时必须绑定用户选定的设备。 |
| 设备身份 | 安装实例标识跨切网保持不变；不得由 IP、MAC 或可编辑显示名充当身份。 |
| 配对关系 | 每客户端独立、可撤销；已过期/被撤销时不提供业务连接，也不降级为免认证。 |
| 当前地址 | 只是短期候选；须由已配对身份验证后方可供业务使用。 |
| 网络代次 | 切网、主动切换设备或地址失效后递增；旧轮次回调不得覆盖当前地址。 |
| 未决写操作 | 以同一业务幂等键关联原操作；切网后不得换键盲目重放。 |

客户端连接态：`未配对 → 发现中 → 验证中 → 就绪 → 地址失效 → 发现中`；有限恢复失败进入`不可用`，被撤销进入`需重新配对`。`就绪`仅表示最近一次身份验证通过，不意味着后续网络必然可用。

## 4. 功能需求

### REQ-LSD-01 服务端发现与身份（P1）

- 启动既有业务 HTTP 服务并确认就绪后，才对目标局域网的有效发现查询返回响应；默认发现端口 39001，业务端口从实际运行配置取得，端口占用明确报错，不静默改用其他端口。
- 查询绑定逻辑服务名、请求轮次及可选的目标设备/配对记录。已配对响应绑定该轮次和配对关系并带可验证认证信息；未知、过期及已撤销的配对不应答。仅在管理员主动开启配对窗口期间允许展示**未认证候选**，不得据此放行业务。
- 仅接受有界、合法的数据报；对重复查询、来源和全局回复量限流，拒绝超长及畸形输入，避免开放式反射。服务端维护可用局域网接口，排除回环、虚拟/VPN/隧道接口，切网后更新有效接口；多网卡的入接口和回包来源必须实测，不做“通配监听自然正确”的假定。
- 设备身份在重启和切网后稳定，进程启动标识每次改变；设备私钥/配对密钥持久化受保护，不进入日志或版本库。管理员能看到本机就绪状态与所选局域网地址，不能通过局域网访问本机管理入口。

### REQ-LSD-02 首次配对与撤销（P1 配对；P2 撤销与完整持久化）

- 管理员在本机主动打开短期配对窗口，小程序扫描包含逻辑服务、设备身份、当前地址候选及独立高熵密钥的短期二维码；先认证当前地址，失败可搜索绑定目标设备的发现响应。二维码过期、取消或已使用后不能创建新配对。
- 激活须证明持有配对密钥且服务端记录为待激活；相同激活请求可重复读取同一结果，不创建第二条关系。未配对设备列表仅供展示，不获得 API 权限。
- 管理员可单独撤销客户端配对；客户端“忘记设备”只清理本地凭据，不冒充服务端撤销。配对凭据、二维码完整内容及认证头不得进入日志、诊断导出或剪贴板历史。
- 小程序本地存储不视为硬件安全区。密钥丢失或服务端设备身份文件重建时重新配对，不复用旧 IP 直接连接。

### REQ-LSD-03 小程序可信寻址（P1/P2）

- 小程序业务层只使用稳定逻辑服务名与受控相对路径；请求层负责解析当前地址，不接受完整 URL、协议相对 URL、任意端口跳转或未知地址重定向。
- 已配对时发现请求只寻找所选设备；客户端从应答实际来源获取候选 IPv4，校验私网地址、合法端口、协议版本、轮次、设备身份、配对 ID 及消息认证，并对候选 HTTP 地址做随机挑战验证；**挑战成功前不向候选地址发送 Bearer、微信 code、导航数据或其他业务请求**。
- 本地记住的旧 IP 只能作为待验证候选；TTL 过期、前台恢复或网络事件后重新验证；同一逻辑名下多设备不按响应先后自动切换。最多同时运行一个同设备恢复任务，候选、并发验证、等待队列及重试次数均有上限。
- 使用安全随机数、受维护且跨 Python/小程序一致的标准 JSON 规范化及 HMAC 实现；任何平台不能可靠实现时停止认证模式交付，不用 `Math.random` 或自制算法替代。

### REQ-LSD-04 切网、超时与安全降级（P1/P2）

- 监听网络变化并在小程序每次回前台时检查地址；即使前后都报告 `wifi`，请求连接错误仍须触发地址失效与新轮次发现。旧轮次回包、超时回调与旧地址的成功响应不得把连接状态改回旧网络。
- 恢复预算、轮次、单候选验证和普通请求超时采用有界默认值，初始参考分别为 12 秒、3 轮、1.5 秒与 5 秒；仅安全读取或已证明幂等的写请求最多自动重试一次。预算耗尽停止自动重试，支持用户手动重试。
- 服务不可达、身份错误或配对撤销时，不继续播报旧导航方向指令、不伪造位置、不得把新服务误当旧会话。连接恢复后仍须按既有 `REQ-SESSION` 重查导航会话、地图版本、权限和定位新鲜度。
- 区分“有明确证据的权限拒绝/身份错误/撤销/协议不兼容”和“原因未知的发现或连接失败”；后者提示检查同网、服务启动、局域网互访与防火墙，不猜测原因。

### REQ-LSD-05 地址二维码降级（P1/P2）

- 广播不可用但 HTTP 单播可达时，服务器展示仅包含设备身份及当前局域网地址的**地址二维码**，不含配对密钥；已配对小程序扫码后仍须挑战验证，未配对须先走配对流程。
- 若 UDP 与 HTTP 均被隔离，扫码不能解锁连接；明确提示换用可互访网络。手输 IP/桌面微信首次配对非首版承诺，需另行评审入口及安全引导。

### REQ-LSD-06 现有请求与业务保持（P1/P2）

- 现有微信登录、Bearer token、会话归属、地图 ETag/分片下载、定位/导航序号与讯飞 URL 签发不因寻址改造而移除。进入已评审的本地模式时，所有指向 PathAI 服务的请求与地图数据下载使用同一**已验证**设备/地址；不得保留另一个固定 `API_BASE_URL` 绕过寻址。
- **局域网与公网分界：** 对局域网内经配对验证的 PathAI 后端地址使用 HTTP，不强制改成 HTTPS；公网请求、既有讯飞 WSS 及其域名要求均不受本方案影响。局域网 HTTP 即使带签名也可被同网旁观者读取，可能暴露微信 code、Bearer、识别文本、签名 URL 与位置/轨迹；切换网络时不得静默把公网请求改送局域网或反之。真实用户数据和公开交付的安全/隐私准入需另行评审这一剩余风险，未获准前仅在受控可信网络使用测试身份与非敏感数据；不能宣称等同于现有 `REQ-PRIVACY` 的 HTTPS 保护。
- 协议认证不替代现有 Bearer 授权。业务请求、响应及配对绑定通过消息认证验证后再交现有业务解析；未经签名、时间窗口错误、nonce 重放、状态码或响应正文被篡改必须拒绝。地图包字节下载/Range、现有 WebSocket 与文件流不在 v1 JSON 双向签名契约内，须定义独立的验证或豁免边界，**未评审前不得把其 HTTP 数据下载视为已受传输认证**。[待确认]
- 对所有现有写端点逐一登记副作用与重试资格；未证明幂等或未有操作状态查询能力时，对网络失联后的未知执行结果显示“待确认”，不得自动重新提交。原有创建导航会话幂等键保持同一次操作不变。

### REQ-LSD-07 用户反馈与运维诊断（P1/P3）

- 设置页显示连接模式、选定设备、状态及可访问的重试/扫码/忘记设备入口；连接不可用时提供震动及可读屏文本，不用颜色作为唯一提示。管理端仅本机显示接口、当前地址、发现端口与配对/撤销状态。
- 脱敏记录发现、验证、恢复阶段与错误分类，绝不记录密钥、二维码、Bearer、原始请求体、完整轨迹或认证头；日志大小和保留期有上限。提示及日志不得将“热点隔离”这种推测说成已证实根因。

## 5. 协议与边界约束（待冻结）

- 以来源方案 v1 的 UDP `DISCOVER`/`OFFER` 字段、1200 字节上限、39001 端口、轮次去重与限流值为候选契约；IP 以 UDP 来源为准，**应答 IP 仍需 HTTP 挑战验证**。
- 来源方案的签名域分离、RFC 8785 JCS、HMAC-SHA256、无填充 Base64URL、128 位挑战/nonce、256 位独立配对密钥及请求/响应原始字节摘要为候选安全基线；必须补齐跨语言测试向量和畸形输入拒绝规则后冻结。
- 来源方案将 JSON HTTP 请求签名绑定 `pairId`、`bootId`、时间、nonce、HTTP 方法、实际路径/查询及原始请求体摘要，响应绑定原请求 nonce、状态码与原始响应体摘要；时间与 nonce 双重约束，进程重启后旧 `bootId` 失效。不能将“认证”表述为“加密”。
- 对既有大地图 Range 响应、未登录的微信换码、管理后台 cookie 流和在线语音凭据签发分别做威胁与接入评审；P0 仅做无凭据隔离原型，完整业务接入待 P2 消息认证、数据流边界及既有规格对齐后执行。局域网 HTTP 明文残余风险不得用消息认证测试通过来掩盖。

## 6. 验收场景（待执行）

1. 指定 Android/iOS 真机对 UDP 广播、单播及同网段 HTTP 分开验证，并记录基础库、微信/系统版本与热点拓扑；失败必须保留失败结论。
2. 管理员开启窗口 → 扫码 → 认证 → 本地无凭据原型探测成功；P2 与受控测试范围冻结后，使用测试身份完成现有业务请求；过期二维码和撤销配对不能取得业务权限。
3. Wi-Fi A 切换 Wi-Fi B 或第三方手机热点，后端 IP 变化后连接同一 `deviceId`；同名服务器、旧 IP 伪服务、迟到旧轮次均不得串连。
4. 广播阻断但单播可达时，扫码地址经挑战后恢复；UDP 与 TCP 均隔离时有界失败且不伪称扫码可解。
5. 切网时并发读请求只运行一个恢复任务；写请求响应丢失时不能重复产生副作用，未具备幂等保证时给出结果未知状态。
6. nonce 重放、认证响应体/状态码篡改、超长/重复键 JSON、洪泛输入均按协议拒绝，日志无敏感数据。
7. 小程序回前台后先恢复可信地址，再执行原有会话、地图和定位校验；服务不可达期间不播报旧转向指令。
8. 分别检查地图摘要与数据下载、微信登录、在线语音、管理后台既有链路；明确标注哪些链路经消息认证、哪些仍为 HTTP 明文、哪些继续走公网，不夸大“完整离线”或“链路加密”。

## 7. 与现有规格的关系

- 当前 `specs/phase-1-indoor-navigation/spec.md` §6 `REQ-BOOT`/`REQ-SESSION`、§6 `REQ-PRIVACY`、§7 API 摘要仍有效；此次确认的局域网 HTTP 与其中“全部业务 API 使用 HTTPS”直接冲突。在代码实施前须将“局域网 HTTP 受控适用范围、公网维持 HTTPS、明文剩余风险及真实用户数据门槛”写入现有规格的版本说明、需求条款和 §10 决策，不得两份规格各说各话。
- `docs/25-第二阶段真机联调检查清单.md` 当前对局域网 IP 及调试绕过的描述只能作为现状，确认方案后增加关闭开发工具绕过的真机可行性测试与安全准入，不得将当前调试配置描述为正式可用。
- P0 原型最初在独立 worktree 中开发；该工作区的改动已按用户后续要求快进合入 `master`，当前仅使用 `D:\code\pathai` 工作区。此工作区变化不改变 P0 隔离探测、不向未认证地址发送业务凭据及 P1/P2 安全门槛。

## 8. 决策记录

### 已确认决策

1. **服务形态（2026-11-01 用户确认）：** 复用现有后端技术栈，不重写为 Go；局域网发现服务与原 Python/FastAPI 业务服务协作。
2. **模式范围（2026-11-01 用户确认）：** 局域网请求保持 HTTP，公网请求不受本方案影响；不把 HMAC 身份认证误称为传输加密。真实用户数据与发布前的剩余风险仍需安全评审。
3. **首版平台（2026-11-01 用户确认）：** Windows＋手机微信；macOS/桌面微信后置。
4. **业务覆盖（2026-11-01 用户确认）：** 全部现有 PathAI 小程序调用统一接入已验证的局域网地址，地图 Range/非 JSON 数据认证边界须单独冻结，讯飞公网链路不改。
5. **实施门槛（2026-11-01 用户确认）：** 先做 P0 真机 UDP、局域网 HTTP 和密码能力验证；不通过不宣称自动发现，P2 安全一致性未通过不宣称完整业务安全。
6. **工作区处理（2026-11-01 用户确认）：** 使用新分支开发，保留当前已有未提交改动所在的工作区不动；通过独立 worktree/副本隔离新分支。
7. **P0 真机入口（2026-11-01 用户确认）：** 新分支临时使用独立隔离探测首屏并跳过业务预热，避免向旧固定 IP 发送微信 code、Bearer 或地图/导航数据；P0 不改变正式业务地址。
8. **工作区归并（2026-11-01 用户确认）：** 将 `feature-localdns` 快进合入本地 `master` 工作区，移除独立 worktree 与已合并分支；当前 `master` 暂时仍是 P0 探测专用构建，未恢复正式导航首屏。
9. **P0 UDP 时序对照（2026-11-01 用户确认并复测）：** 第三轮真机报告显示 `onListening` 后异步错误，但原实现 `bind()` 后立即 `send()`，不能凭错误发生阶段推断发送时已就绪。现仅在 `onListening` 后发送一次，超时或错误后不再发送；iPhone XS Max 热点宿主场景复测仍异步报错，普通同网 Wi-Fi 的无凭据 UDP→HTTP 闭环成功，不能据此断言热点失败根因或 P0 整体可行性。

### 模块实现前冻结项

- 基础库下限、目标机型/微信版本、网段/热点设备、UDP 广播及本地 HTTP 在**关闭调试绕过**时的实测可行性；不通过时保留扫码单播或重新评估客户端形态。
- 同源业务 HTTP 与既有 HTTPS 规格的文本对齐、可处理的数据敏感等级、微信登录/语音公网依赖边界、密钥存储及设备撤销策略；真实用户数据的明文风险另行审查。

- 本地后端服务发现的独立进程/同进程生命周期、本机管理端口、持久化身份目录、Windows 防火墙策略与多网卡限制。
