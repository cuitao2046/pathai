   位置：[client API](D:/code/pathai/client/core/http/api-client.ts:4)、[后端认证](D:/code/pathai/backend/pathai_backend/auth.py:118)、[地图路由](D:/code/pathai/backend/pathai_backend/routers/map.py:24)。

2. **[P1，已复现] LLM 可以把“左转”改成“右转”，仍通过导航文案校验。**

   位置：[文本校验](D:/code/pathai/backend/pathai_backend/nav_text.py:108)。

   _validated_texts 只检查 ID、长度和原文数字是否仍存在。“前方5米向左转”改成“前方5米向右转”会被接受，虽然结构化 action 没变，用户实际听到的指令已经相反。上下楼、禁止通行和风险提示也没有语义不变量保护。

   建议：方向、距离、楼层、否定条件和风险提示采用确定性模板输出；LLM 仅处理不影响行动的补充描述。若保留完整改写，必须建立动作/方向/数值/否定语义校验，任何不一致回退原文。增加左右互换、上下互换和删除危险提示的测试。

3. **[P1，静态确认] 连续断网时导航仍保留 active，缺少本地安全暂停。**

   位置：[导航更新异常](D:/code/pathai/client/core/nav/nav-session-controller.ts:472)、[前台恢复](D:/code/pathai/client/core/nav/nav-session-controller.ts:349)。

   sendUpdate 对普通网络错误/超时直接丢弃本拍，未根据“距上次有效导航响应多久”进入暂停。定位失败时即使 reportUnavailable，也要依靠同一条已经不可达的链路通知服务端。回前台查询失败还会重新启动采集。结果可能是界面仍 active、旧指令和方向箭头仍有效，但实际导航状态早已未知。

   建议：增加本地网络失联/响应新鲜度看门狗；超阈值立即停止可执行旧指令、箭头和转向节拍，给出一次安全提示。继续尝试连接，但仅在服务器会话校验与新鲜定位均成功后恢复引导。不能只依赖服务端 recovering。

4. **[P1，已复现] 定位管线 stop 不能隔离已启动的异步任务，重启后可能生成双循环。**

   位置：[管线 start/stop](D:/code/pathai/client/core/position/location-pipeline.ts:85)、[结果投递](D:/code/pathai/client/core/position/location-pipeline.ts:229)。

   HTTP 完成后没有 running 或 generation 校验，停止后仍触发 onEstimate。另一个复现是 start A 尚未完成时 stop，再启动 B；A 后续完成仍 schedule，最终存在两个定时器。tick 也没有 single-flight 门禁，手动 tick 与自动定时可并发。

   建议：start/stop 递增 generation，所有 await 后、回调投递前检查会话代际；stop 时取消可取消的请求；tick 单飞，schedule 前先释放旧计时器。验收应断言停止后零回调、快速重启只有一个循环。

5. **[P1，静态确认] client 固定旧地图，backend 定位却只接受最新地图，发布会打断正在使用的客户端。**

   位置：[客户端后台更新策略](D:/code/pathai/client/core/map/map-service.ts:271)、[定位版本拒绝](D:/code/pathai/backend/pathai_backend/routers/location.py:115)、[创建会话版本拒绝](D:/code/pathai/backend/pathai_backend/routers/nav.py:105)。

   客户端后台缓存新包但本次继续使用旧包；后台一发布新版，旧版本定位请求立即 409 MAP_VERSION_CONFLICT。当前管线没有自动刷新并重新绑定会话的恢复流程。旧导航 updates 仍按 session.map_version 读取，形成同一导航链路中互相冲突的版本策略。

   建议：允许活跃会话在可控保留窗口内继续使用其固定地图及定位参数；新会话再升级。若新版必须强制切换，返回明确失效事件，由客户端暂停导航、加载新包并重新确认路线，而非无限重试旧版本。

6. **[P1，已复现] 偏航判定计算“到节点距离”，不是“到路线距离”。**

   位置：[最近路线计算](D:/code/pathai/backend/pathai_backend/routers/nav.py:249)、[偏航调用](D:/code/pathai/backend/pathai_backend/routers/nav.py:327)。

   当路线为 (0,0) 到 (20,0)，用户在 (10,0) 正中间，当前函数返回距离 10 米；超过 OFF_ROUTE_M=8，会在完全沿路线行走时判定偏航。remaining 同样依赖节点近似，触发时机也可能抖动。

   建议：计算同层点到各线段的正交投影距离和沿线里程，以投影进度计算剩余距离；对偏航和路径进度增加滞回、连续确认，避免平行走廊或折返路线跳段。测试覆盖长边中点、拐角、平行路线和楼层切换。

7. **[P1，静态确认] 定位/导航未校验观测时间新鲜度，过期位置仍可触发到达。**

   位置：[定位请求处理](D:/code/pathai/backend/pathai_backend/routers/location.py:96)、[到达判断](D:/code/pathai/backend/pathai_backend/routers/nav.py:290)。

   collectedAt/observedAt 有 datetime 类型约束，但没有最大过期窗口、未来时钟容差以及观测时间单调检查。导航到达只根据 quality、floorId 和距离判断；sequence 更新不等于观测时间更新。延迟的可信坐标或重复缓存数据可以使导航错误推进乃至自动结束。

   建议：检查批次和单信标观测年龄、未来时间和会话最后可信观测时间；不新鲜的数据只驱动暂停，不能触发转向或到达。到达增加新鲜可信观测的连续确认，并考虑所在区域/拓扑可达性，避免隔墙近距离直接到达。

8. **[P1，静态确认] 页面异常收尾会丢失创建会话的幂等键，超时后可能重复创建。**

   位置：[控制器暂存幂等键](D:/code/pathai/client/core/nav/nav-session-controller.ts:160)、[页面创建失败处理](D:/code/pathai/client/pages/map/map.ts:2342)、[清理控制器](D:/code/pathai/client/pages/map/map.ts:2699)。

   控制器在网络/5xx 时本来保留 pendingIdempotencyKey；但页面 catch 会调用 onDismissNav，将 controller 置空。若后端已经提交、响应却超时，下次尝试新建控制器就换了键，无法复用已创建会话。后台默认也只清理终态导航，遗留 active 会话会长期存在。

   建议：将“创建结果未知”作为可恢复状态保存，保持同一冻结请求和幂等键；重新查询/重放确认结果后再决定清理。服务端增加活动会话闲置超时策略。补充“提交成功但客户端丢响应”跨端测试。

9. **[P2，已复现] 查周边功能的请求/响应契约尚未在 backend 实现。**

   位置：[请求字段](D:/code/pathai/client/core/position/location-pipeline.ts:181)、[查询调用](D:/code/pathai/client/services/location-query.service.ts:260)、[后端 schema](D:/code/pathai/backend/pathai_backend/schemas/location.py:49)。

   client 发送 includeSurroundings=true，backend LocationEstimateRequest 没有该字段，StrictModel extra=forbid，实际请求 422。响应模型和定位路由也没有 surroundings 输出，不能只删掉请求字段或忽略未知字段就认为功能完成。

   建议：补齐后端周边查询参数、带方向和距离的响应及质量降级语义；在实现前通过能力协商隐藏入口或明确提示暂不支持。用 OpenAPI 生成/校验客户端类型，加入真实 JSON 契约测试。

10. **[P2，静态确认] 定位序号恢复需要的 lastSequence 未返回，且服务端更新有并发竞争。**

    位置：[后端水位校验](D:/code/pathai/backend/pathai_backend/routers/location.py:64)、[水位推进](D:/code/pathai/backend/pathai_backend/routers/location.py:76)、[客户端恢复](D:/code/pathai/client/core/position/location-pipeline.ts:208)。

    客户端仅在 error.details.lastSequence 为 number 时追平，但后端 STALE_LOCATION_BATCH 没有设置 details。因此水位异常时快速恢复分支不会生效。服务端先读后写水位没有锁/CAS，两个首次并发请求可能主键冲突，已有行的并发请求也可能把较大水位覆盖成较小值。

    建议：统一错误信封返回 lastSequence；用原子 max/upsert 或带条件更新保证单调水位，必要时进行有限冲突重试。加入同主体同场所两个并发定位请求的数据库测试。

11. **[P2，静态确认] 已解析的服务地址永久缓存，IP 变化后无法在本进程恢复发现。**

    位置：[地址门禁](D:/code/pathai/client/services/service-endpoint.ts:71)。

    current 非空时直接返回，没有运行期失效/重探测接口；API 请求失败也不通知解析器。电脑切网、DHCP 换 IP 或手机换热点后，即便新后端在线，也会持续访问旧地址，通常只能重启小程序。

    建议：引入 endpoint generation 和失效机制，网络变化或连续连接失败时受控重发现。只自动重试明确可安全重放的读取请求；导航创建等写请求必须结合既有幂等键确认结果。

13. **[P2，静态确认] 地图发布缺少跨请求/跨进程互斥，版本可能被覆盖且 worker 快照不一致。**

    位置：[版本分配及写文件](D:/code/pathai/backend/pathai_backend/admin/publish.py:87)、[局部刷新](D:/code/pathai/backend/pathai_backend/admin/publish.py:123)、[发布路由](D:/code/pathai/backend/pathai_backend/routers/admin_maps.py:346)。

    两个发布请求可以根据同一内存快照获得相同版本，同时通过 exists 检查，最后 os.replace 后写者覆盖先写者。刷新仅更新当前 app.state，其他 worker 不会感知最新文件，进一步造成定位版本判定不一致。首次并发 ensure_admin_account 也采用先读再插入，在多 worker 启动下存在唯一约束竞争。

    建议：数据库事务/场所级锁负责版本号分配及发布 CAS；文件采用不可覆盖提交，数据库记录发布状态与内容哈希；所有 worker 通过版本号轮询或发布通知更新快照。账户初始化改为幂等 upsert 或迁移期一次性初始化。单 worker 部署也应测试同一时刻两个发布请求。

14. **[P2，静态确认] 管理员使用公开默认密码，登录无节流。**

    位置：[默认凭据](D:/code/pathai/backend/pathai_backend/admin/service.py:23)、[登录接口](D:/code/pathai/backend/pathai_backend/routers/admin_auth.py:26)。

    首次启动直接创建 admin/admin，must_change_password 仅阻止已登录用户继续使用管理功能，不能防止其他人抢先登录并修改密码。登录和改密失败也没有账户/IP 尝试限制；每次失败执行 scrypt，在可访问的部署上同时构成暴力尝试和资源消耗风险。

    建议：初始化凭据由部署端注入，或生成一次性随机引导口令；首次设置限制到本机/受控引导通道。对登录、验证当前密码添加账户和来源维度的速率限制与审计，避免全局锁定造成拒绝服务。
