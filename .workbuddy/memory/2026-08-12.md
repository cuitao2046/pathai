- ⚠️ 异常：ff-merge 后 `git status` 显示 docs/(01-14/AOD/task/reference)、src/(各 __init__.py、skeleton/*、tools/*、rendering/render_map.py) 大量文件被标记工作区删除，仅 fdd9e97 新增文件(docs/code-review*、src/common、src/geometry)保留。
- **精确根因（取证后修正）**：Windows Git 2.54 + `core.fscache=true`。reflog 证实顺序为 `checkout master`(HEAD@{1}, 工作区先回退到 ca9e76f 删掉分支多出的文件) → `merge --ff-only`(HEAD@{0}, master 快进到 fdd9e97)。ff-merge 本应把文件写回工作区，但 fscache 在同一回合「删除+重建大量文件」时返回陈旧元数据，使 Git 跳过物化步骤 → **仅工作区缺文件，索引/对象库始终正确**。关键证据：`git checkout -- .` 从索引(=HEAD fdd9e97 完整 127 文件)一键恢复，证明数据零丢失。`origin/master` 本地引用缺失(rev-parse 报 unknown revision)是**次要/伴随现象**（远端跟踪引用在本环境不持久，只在 fetch 后存在），不是工作区删除的直接原因。
- 修复：`git checkout -- .` 重建工作区 → status 转 clean。
- 🛡️ **防呆流程（铁律级，替代原「先 fetch」经验）**：本仓库已 `git config core.fscache false`(本地可逆，消除陈旧物化 bug 类)。合入标准序：① `git fetch --prune`(建 origin/master 基线+刷新缓存) → ② `git checkout master` → ③ `git merge --ff-only <分支>` → ④ **`git reset --hard HEAD`**(强制工作区==HEAD，消灭任何部分物化残留) → ⑤ `git status --short` **必须为 0 行** 才继续 → ⑥ `git push origin master` → ⑦ `git branch -d <分支>` + `git push origin --delete <分支>`。第④步是保险核心，无论根因是哪类物化失败都能兜底。
